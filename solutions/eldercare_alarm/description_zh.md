## 这个方案做什么

把跌倒检测器已经在发布的 MQTT 事件流，变成有人负责的告警。服务按区域盯三件事：跌倒事件、
区域持续无人、区域内有人但持续不动。任意一件成立就开一条告警，由值班人在单页控制台上确认
或驳回，确认后的告警以 webhook 或 MQTT 发出去。

检测本身一点没变。本方案不含任何推理代码——它消费
[EdgeFallKit](https://github.com/suharvest/edgefallkit) 检测器的 `fall_result_v1` 负载，
并复用它已发布的镜像。它补上的是"摄像头看见了"与"有人处理了"之间那一段：区域、超时、
带取证窗口的状态机、SQLite 审计链、幂等投递，以及通知端不可达时不会丢消息的队列。

## 你会得到什么

**三类告警，逐区域配置。** 跌倒事件由检测器送来。区域无人与区域静止在这里判定，依据是
`person_count` 以及每个被跟踪者 bbox 中心的位移。每个区域各有自己的 `no_person_timeout`
与 `no_motion_timeout`——卫生间和卧室不是同一个问题。

**有确认环节，不是一推了之。** 告警先进取证窗口（5 s），再等人工处理（60 s）。确认和驳回
都会把操作者记在这条告警上。窗口内无人应答时，默认按"疑似成立"处理并通知；可通过
`statemachine.confirm_timeout_action` 改成相反的默认值。

**投递可审计。** 确认后的告警必须在 5 s 内完成通知，否则转入 `escalated` 并停在那里，
每 30 s 重试。即使重试成功，`escalated` 也不回退到 `notified`，让审计链保留"曾经超期"这个
事实。每条通知带幂等键（`zone:kind:event_timestamp:global_event_id`），告警表与通知表都在
其上建了唯一索引——事件重放和重试都产生不了重复告警或重复送达。

**通知里没有视频。** 负载是告警 id、类型、区域、流编号、时间戳与操作者。没有快照，没有短片。
抓帧功能只有一个配置开关（`web.snapshot_enabled`），默认关闭，背后尚无实现。

**默认全程本地。** 整条链路没有云端依赖。事件、状态转换、操作者与送达回执保留 90 天；
媒体文件若将来启用，保留 7 天并每日清理。

## 适合接到哪里

- **养老机构与居家照护**——卫生间或卧室里，跌倒本来要等到下一次查房才会被发现；而"从昨晚起
  厨房就没人进过"同样是一个信号。
- **已经有跌倒检测的现场**——reCamera 套餐在已经跑着检测器的摄像头之上加一层告警，不动摄像头。
- **需要把告警落到人头上的场合**——确认环节和审计存储就是为交接班和事后复盘准备的。

## 实际效果如何

**本系统不是医疗器械，也不是经过认证的紧急响应产品。** 它不用于诊断、治疗，也不替代护理人员
的判断。告警只是提示，判断与处置责任在人。

下面第一张表里的所有数字都是在一台笔记本上、用回放器代替摄像头测出来的——**本机回放、非真机**。
测量当日三台目标设备全部离线，因此本包内没有任何真机数字。

**怎么测的**

- 日期 2026-09-05，运行目录为 eldercare-alarm 项目下的 `evaluation/runs/2026-09-05-smoke/`。
  原始输出在 `raw/`，测试条件在 `conditions.yaml`，每行指标各有一份 `boundary.<metric>.yaml`。
- 主机：MacBook，macOS 15（Darwin 25.5.0），arm64。本机回环网络。未走容器，直接跑服务。
- 评测脚本驱动的是真实的 `AlarmService`——真状态机、真 SQLite、真 HTTP webhook——只把摄像头
  换成回放器。因此这些数字描述的是告警链路本身，**不含推理耗时，也不含跨机网络**。
- 本次把状态机窗口缩短了（取证 1 s + 自动确认 1 s，而非默认的 5 s + 60 s），所以时延绝对值
  是这次配置的属性，不是现场的属性。
- 四份 `boundary.*.yaml` 里只有 `stable` 一档有值，`degrading` 与 `failure` 全为 `null`：
  本次没有加压到退化，也就没有测到边界。
- `reproduced_by: null`——单人单次，未经第二人复现。

**完全没有验证过的部分。** 没有任何真机运行。Jetson 的 `publish_empty_frames` 覆盖、

P95 2751 ms，第 6 次起被通知层自带的"600 s 内最多 5 条"限速悄悄拦下，
这是设计行为，不是故障。USB 断开重连测试未做（超出本轮授权范围）。详见
`eldercare-alarm/evaluation/runs/2026-09-06-recamera-one/results.md`。

## 输出接口

| 输出 | 位置 | 内容 |
|---|---|---|
| 告警列表与操作 | HTTP 8080 端口，`/api/alarms` 与 `/` 页面 | 告警记录，含状态、区域、流编号、时间戳与操作者；确认与驳回 |
| 通知 | HTTP POST 到你的 webhook 地址 | 告警 id、类型、区域、流编号、时间戳、操作者，另带幂等键请求头——无快照、无视频 |
| 告警总线（可选，默认关闭） | MQTT 1883 端口，主题 `eldercare/alarm/<区域 id>` | 负载与 webhook 相同 |
| 检测结果（输入） | MQTT 1883 端口，主题 `<设备名>/fall-detection/results/<流编号>` | 本服务消费的 `fall_result_v1` 事件流 |

`<设备名>` 是主题的第一段，在部署表单里自己填。`stream_id` 一律从消息负载里读，绝不从主题解析
——broker 改写或桥接加前缀都不会让某个区域被悄悄接错。

## 方案对比

**IP 摄像头 + reComputer J（Orin）** 把所有东西放在一台上：检测器、告警服务、broker 与确认
页面。三个套餐里它能带的路数最多；首次部署会在设备上构建 TensorRT 引擎，这也是它耗时最长的
原因。现场已有摄像头、但还没有网关主机时选它。

**IP 摄像头 + reComputer R（Hailo）** 是同一套栈跑在 Hailo-8 上，检测器热路径为原生 C++，
姿态模型是下载已编译好的 HEF 而不是在设备上构建。它与 HailoRT 4.21 的 ABI 绑定——插件、
用户库与驱动必须同版本一起动——所以这类硬件和这个运行时版本已经装好时选它。

**reCamera + 告警网关** 是唯一一个不为检测新装任何东西的套餐。摄像头本来就在跑检测，告警
服务放到旁边的网关上。这一步是人工的：网关是现场手上现成的机器，部署表单没有对应的设备类型
可以寻址它。摄像头已经就位、又不打算再加一台算力盒子时选它。

## 使用须知

- **区域是画面上的归一化矩形。** 移动或重新对准摄像头会让区域划分失效，而且不会报任何错——
  矩形还在，只是盖到了房间的另一块地方。任何物理调整之后都要重新核对区域。
- **`no_motion` 在睡眠时段会触发**，除非区域排除床位，或者超时长于一次正常午睡。motion 的
  判据是被跟踪者 bbox 中心位移超过 `motion_threshold`（默认 0.02，归一化），不是光流也不是
  关键点速度——被子下的小幅动作不算。
- **Jetson 上的检测器必须发布空帧。** 它默认在无人时什么都不发，会让 `no_person` 超时收不到
  任何输入。Orin 套餐已替你把 `publish_empty_frames` 置为 true；如果你用设备上原有的配置
  替换了随包的检测器配置，记得再设一次。Hailo 运行时没有这个开关，也不需要。
- **结构上就是单点。** 一台摄像头、一个检测器、一个服务。摄像头掉线时，不会有"告警没了"的
  告警；要监控这一点，看检测器那条 retained 的 MQTT 在线状态主题。
- **遮挡可能造成 `no_person` 误报。** 区域要等人重新被看见才会重新武装，所以一次遮挡只产生
  一条告警而不是一串——但它确实会产生一条。
- **broker 从哪来因套餐而异。** Orin 与 Hailo 会连同检测器一起起一个；reCamera 网关既可以
  自己起一个，也可以指向摄像头已经在发的那个。随包的 broker 允许匿名连接，仅供在可信局域网内
  开通调试——设备能被局域网以外访问之前，先加上账号密码与 TLS。
- **告警服务镜像尚未发布。** 打包时它只作为上游项目 `docker/Dockerfile` 的本地构建存在。
  Orin 与 Hailo 套餐能部署成功之前，需要先自行构建并改 tag，或者把它推上去。
- **Telegram 与邮件只是接口占位。** 选中它们会抛错并进重试队列，而不是静默丢弃通知——这是
  预期行为，但它们不是可用的通道。

## 语音确认（可选）

默认关闭，关闭时方案其余部分与之前完全一致。开启后，跌倒告警一被触发，服务就会向房间里
播一句提示——"您还好吗？请回答"——并录几秒钟回答；这一步与 5 秒取证窗口并行，不是等它结束之后。

求救、完全没有回答、听不明白的回答，都会立即确认告警并跳过剩余的人工窗口。
"我没事"默认**不**结案：它只给告警打上待复核标记，原有时序照常走；要直接结案就设
`on_ok: dismiss`。这种不对称正是重点——把真实跌倒时的求救听成"我没事"会压掉一条真告警，
而确认一条本不必确认的告警只花操作员几秒钟。同样的道理，同一句话里求救词压过安全词，
词表识别不出的说法一律确认而不是等待。

音频硬件是接在局域网计算盒上的 USB 麦克风与扬声器，另需一个 OpenVoiceStream 实例提供
TTS 与流式 ASR。音频不走摄像头：两款 reCamera 都没有确认可用的麦克风，SG2002 更是跑不了
本地 ASR。同机部署时 TTS 与 ASR 会和检测器争抢 CPU、加速器与内存——限制单会话、
提示音预先生成、OVS 超时一律 fail-safe 确认，就是为了不让这种争抢吃掉一条告警。

**隐私。** 音频不落盘。原始 PCM 只在一次录音窗口内驻留内存，判定产出后即释放。
持久化的是 verdict、置信度、耗时与转写文本；把 `store_transcript` 设为 `false` 连文本也不存，
审计里只留 verdict。通知负载增加同样这几个字段，仍然不含快照和视频。
