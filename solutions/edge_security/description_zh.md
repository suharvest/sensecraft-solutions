## 这个方案能帮你做什么

画一条线或圈一块区域，有人越过就报警。禁区入侵、越线和滞留告警，判定就在现场那台边缘盒子上完成。浏览器里画规则、看视频墙、逐条处理告警，视频不出场地。

- **禁区入侵**——有人进入你在画面上画出的多边形。
- **越线**——有人跨过一条线。规则可以限定方向，因此“进”与“出”是两条不同的告警，反向通过不误报。
- **区域滞留**——有人在区域内停留超过你设定的时长，在入侵告警之外再叠加一条滞留告警，而不是替换它。

探测层和判定层是两个进程，通过 MQTT 通信：一台 hub 可以接入多台不同种类、装在不同房间的检测器，值班人员只看一份告警列表。

## 核心价值

- **摄像头完全复用**：直接接入标准 RTSP H.264 视频流，现场已安装的机位不用更换。
- **无需额外服务器**：检测、跟踪、规则判定、告警持久化和 Web 工作台跑在同一台边缘主机上，无需云端依赖。
- **视频数据不出场地**：视频流完全在本地闭环解码与推理，仅告警事件与现场抓拍截图通过 MQTT 发出。
- **完整值班工作台**：自适应多路视频墙（1–9 格）、HDMI 全屏大屏模式、实时告警逐条处置与 CSV 导出。
- **画面上直接画规则**：在实时视频画面上 4 点画禁区、2 点画越线，保存即生效，无需重启服务。

## 适用场景

边界画得出来、摄像头装得住、有人越界要马上知道的地方：

- **周界与受限区域**——配电房、危化品库、机房门口。画一个禁区，有人进去即刻报警。
- **通道与出入口**——在走廊或大门拉一条线，只算单向通行，反向走不报。
- **停留即异常的点位**——关键设备旁、物料货架前。超过设定时长未离开，升级为滞留告警。

**使用须知与限制**：
- 目标为人员检测，不适用车辆、包裹、工具等非人员目标。
- 摄像头装好后不能再移动，因为几何规则直接锚定在该画角上，移动后需重新画线。

## 值班人员实际看到什么

hub 自带的浏览器工作台，中英文均可：

- **工作台**——告警列表，每条带现场快照；可按设备、视频流、规则和时间筛选；可标记已确认或误报，最近一次操作有撤销条；批量模式用于清积压；筛选结果可导出 CSV。
- **规则**——边界直接画在从检测器取回的实时画面上，画在哪就是哪。规则修改带版本号。
- **设备**——哪些检测器在线、各自的检测速率，以及每台是走硬解还是 CPU 解码。

告警同时回发到 MQTT，NVR、PLC 网关或你已有的告警系统可以直接订阅，不必轮询接口。

## 实测效果

下面每个数字都来自实测台架，不是规格书。时刻偏差来自一段 130 秒的 1280x720 H.264 视频：
其中每一次越线和进入区域的发生帧是已知的，以 5 fps 通过 RTSP 回放进真实流水线后逐条比对。

| 现场能得到什么 | 典型值 | 设备 |
|---|---|---|
| 越线发生到告警 | **0.109–0.268 秒** | Jetson Orin NX 16GB |
| 进入禁区发生到告警 | **0.090 秒** | 同上 |
| 滞留判定与真值的偏差 | **0.090–0.290 秒** | 同上 |
| 方向判定 | **8/8 正确**，无反向误报 | 同上 |
| 采集到告警 | **P50 117.4 ms**（P95 297.0 ms） | 同上 |

每条告警都存下了一张可解码的 JPEG 现场截图，8/8。
reComputer RK3588 系列在同一段素材上落在同一区间（越线 0.085–0.248 秒、方向 8/8、
快照 8/8），所以**选硬件看路数，不看判定精度**。

Jetson 数据取自一台 Orin NX 16GB，系统 JetPack 6.1（L4T R36.4.3）；RK3588 数据取自
同款 SoC 的开发板，内核 6.1.84，尚未在 reComputer RK3588 系列整机上复测。

**精度。** RK3588 上 int8 相对 fp16，COCO person：AP@.5:.95 掉 0.52，小目标掉 0.61。
该平台默认用 int8，因为流水线内快 42%，代价就是这个。Jetson 走 FP16，不存在量化损失。

## 一台 Jetson 能带几路摄像头

下面这些决定性数据都测自 Orin NX 16GB。

- **GPU 上限：236 次推理/秒**（所有上下文合计）。工作进程满负荷跑：1 个 → 166.7/s，
  2 个 → 231.2/s，4 个 → 237.0/s，8 个 → 235.8/s。从两个进程起总吞吐就不再增长，
  说明 GPU 是共享瓶颈，饱和点就在这里。
- **每多一个检测器进程多占 208 MB 统一内存**，各自持有自己的 engine、context 和 Python
  运行时。系统已用内存：基线 3977 MB → 1/2/3/4 个进程时 4172／4394／4600／4822 MB。
- **在真实速率下互不干扰。** 四个进程各自以 5 fps 推理，实测 p50 分别为 4.02／4.07／
  4.04／4.02 ms，与单进程独跑没有区别。

| 路数（1080p @ 15 fps） | 做法 |
|---|---|
| **1 – 8 路** | 一路摄像头起一个检测器容器，不需要写任何新代码。8 路占板卡 15.6 GB 中的 1.7 GB，120 次推理/秒对 236 的上限约 51% GPU，单帧延迟仍停在空载水平，不会进入排队区间。 |
| **8 – 16 路** | 改用动态 batch 的 engine，前提是有人先把批量吞吐实测出来。批量能摊薄每次推理 1.21 ms 的 enqueue 开销，但一个 batch 必须等最慢的那一路交出帧才能下发，每条告警最多要多等 67 ms。 |
| **16 路以上、4K，或需要拼接大屏** | 上 DeepStream。超过 16 路后 CPU 侧的预处理才真的成为瓶颈，只有 NVMM 零拷贝能绕开。另外 JetPack 6.1 版的 DeepStream 7.x 装完要 1.5–2 GB 磁盘，并且把你锁死在一组 JetPack／`pyds` 版本上。 |

上表的数据都是单路 720p 5 fps 实测的，单路占单核 8.5–12.5%。按 8 路规格上机之前，
请在自己的目标分辨率上实测两项：1080p 15 fps 下每路的 CPU 占用，以及 NVDEC 并发
8 路 1080p15 的会话容量。

## 哪些经过验证

已在真实硬件上验证：

- Jetson TensorRT 检测器，在一台 Orin NX 16GB 上，且确认它真的在用 NVDEC 硬解——
  容器进程持有 `/dev/v4l2-nvdec`，协商出的 caps 带 NVMM 来源标记——而不是已经悄悄
  退回 CPU。
- RK3588 检测器，同样做了针对板卡硬解的确认。
- 两个套餐都以容器形式完整部署过，用的就是这里随方案下发的 compose 文件与部署步骤。
- hub——规则、冷却、告警生命周期、存储、REST 与 WebSocket 接口。
- 浏览器工作台。
- 上表中的真值断言。

**broker 接受匿名连接，但只有「共享 Hub」套餐会把它暴露出去。** 每个套餐的 mosquitto
都是 `allow_anonymous true`。三个单机套餐里它绑在 loopback 上——检测器和 hub 走 compose
内部网络连它，局域网上没有任何东西能往里发消息。「共享 Hub」套餐是有意的例外:远程检测器
必须能连到 1883，所以那一个监听在网络上，任何能连到该端口的机器都可以往检测主题发消息
——包括伪造的检测结果和判定事件，而安防工作台会把它们当成真告警显示。把那台主机放到管理网
或摄像头 VLAN，并在 `assets/hub/config/mosquitto.conf` 里加 `password_file`、在各检测器
配置里配上对应凭据。如果你为了接第二台检测器而把某个单机套餐的 broker 重新发布到局域网，
同样适用:改端口绑定的同时要加密码文件，不能只做前一半。8090 上的工作台不受影响，它需要登录。

上面这些数字的适用范围：

- **reCamera 的探测节点尚未构建。** 报文契约已公开，新增它不需要改动 hub。Hailo 的
  探测节点已构建并实测，见 Hailo 套餐。
- **多路数据是用工作进程测的 GPU 与内存开销**，不是八台摄像头配八套规则跑出来的。
  按自己的路数上机之前先做一轮现场试点。
- **小目标精度的结论只在 COCO 上成立。** 标定素材里几乎没有远处的人，因此广角俯拍、
  人在 30 m 外的场地超出了实测范围。正式采用前请用该场地的实拍素材重新测一遍。

## 硬件要求

| 角色 | 要求 |
|---|---|
| 摄像头 | 任意固定机位的 RTSP 摄像头。必须是 H.264——Jetson 与 RK3588 套餐走硬解，Hailo 套餐走 CPU 软解（Pi 5 没有 H.264 硬解）。规则画好之后摄像头不能再移动。 |
| 探测节点 | 一台 JetPack 6.x 的 Jetson Orin（Orin Nano 8GB 或 Orin NX 16GB），装有 TensorRT 与 nvidia 容器运行时；**或者**一块装有 `rknpu2` 运行时和 `rknn_toolkit_lite2` 的 RK3588 板卡；**或者**一台 PCIe 插槽上装了 Hailo-8、并装好驱动与版本匹配 HailoRT 的 reComputer Industrial R20 系列。 |
| 汇聚主机 | 不需要。broker 和 hub 就跑在做检测的那台机器上。只有可选的「共享 Hub」套餐才需要另一台常开、装有 Docker 的 arm64 或 x86_64 机器。 |
| 磁盘 | Jetson 与 RK3588 套餐在检测机器上约需 6 GB 空闲：检测器镜像、hub 镜像、在本机构建的 TensorRT 引擎，以及告警数据库。Hailo 套餐约需 4 GB，它不构建引擎。 |
| 网络 | 检测器要能连到 hub 的 1883 端口，值班终端要能连到 8090。摄像头预览端口 8099 必须能被值班浏览器访问，否则规则编辑器没有底图。**1883 上的 broker 接受匿名连接**——放到通用网络之前先看下面那条说明。 |

## 怎么选套餐

三个部署套餐都是单机自足：broker、hub 和检测器都在同一台机器上，部署完成后工作台就
由这台机器提供。

- **Jetson 单机部署**——一台 Jetson Orin 看一路摄像头，推理走 TensorRT、解码走 NVDEC。
  引擎在部署过程中于本机构建，首次安装因此多花约五分钟。
- **RK3588 单机部署**——一块 RK3588 板卡看一路摄像头，推理走 NPU、解码走板载硬解。
  同时跑检测器时，这块板卡上 hub 本身占**单核 3.7%、RSS 52.8 MB**，一块板带得动两者。
- **Hailo 单机部署**——一台装了 Hailo-8 的 reComputer Industrial R20 系列看一路摄像头，推理走加速器。
  1280x720 实测：**单次推理 7.7 ms，全管线 9.5 ms，CPU 占单核 8.7–13.0%**。
  解码在 CPU 上，这是主路径而不是降级：该板卡没有 H.264 硬解，所以检测器的 CPU 占用里
  同时包含解码和推理。
- **共享 Hub（可选扩展）**——它本身不是一条部署路径。只有当你已经有多台检测设备在跑、
  希望它们共用一份告警列表时才用：在另一台常开机器上装 broker 和 hub，再把各台检测器
  的 `mqtt_host` 指过去。汇聚主机本身不需要加速器——在一块 RK3588 板卡上同时承载
  两个检测器实测占**单核 3.7%、RSS 52.8 MB**。

## 开始之前值得知道的一种失效形态

检测器跟不上摄像头时，表现出来的不是"慢"，而是**误报**。帧成簇到达，相邻两次上报的
间隔超过跟踪器的容忍时间，跟踪器给同一个人发了新的编号，而这个新编号"从未进过区域"，
于是区域告警又报了一次。看上去像规则引擎坏了，其实不是。

单路摄像头下两个套餐都离这个边界很远——Jetson 检测器在 200 ms 的帧周期里只花 7.24 ms，
RK3588 是 44.3 ms——但如果你往一台机器上接太多路摄像头，或在旁边跑别的重负载，最先
出现的就是这个现象。怀疑规则之前，先看设备页上的检测速率。
