## 与「工业安防（Jetson 边缘部署）」的关系

本方案是既有 `industrial_security_jetson` 的多平台重做版：三条规则（禁区入侵、越线、
区域滞留）和浏览器看板保持一致，但探测层与判定层被拆成两个进程，通过一份公开的 MQTT
报文契约通信。正因为如此，RK3588 板卡现在可以独立跑完整套，其他探测硬件后续接入也不
需要改动 hub。

**选哪一个只取决于一点：本方案没有 TensorRT 路径。** 这里的 Jetson 套餐跑的是
CPU / ONNX 检测器，GPU 空闲。

- **需要 Jetson 上的 GPU 推理**——继续用**工业安防（Jetson 边缘部署）**，两者之中只有
  它带 TensorRT 检测器。
- **部署在 RK3588 上**，或部署在 CPU 检测器就够快的任意 arm64 / x86_64 机器上，
  **或者需要告警走 MQTT、多台检测器共用一份告警列表**——用本方案。既有方案只支持
  Jetson。

TensorRT 探测层正在本方案中补齐。补齐之后，本方案将正式取代
`industrial_security_jetson`，既有方案下线。

## 这个方案做什么

摄像头看现场，边缘盒子在画面里找人，一台 hub 把结果判成三类告警，汇成一份可以逐条
处理的列表：

- **禁区入侵**——有人进入你在画面上画出的多边形。
- **越线**——有人跨过一条线。规则可以限定方向，因此"进院"和"出院"是两条不同的告警。
- **区域滞留**——有人在区域内停留超过你设定的时长，在入侵告警之外再出一条，而不是
  替换它。

探测层和判定层是两个进程，通过 MQTT 通信。这也是它区别于单摄像头演示的地方：一台 hub
可以带多台不同种类、装在不同房间的检测器，值班人员只看一份告警列表。

## 值班人员实际看到什么

hub 自带的浏览器工作台，中英文均可：

- **工作台**——告警列表，每条带现场快照；可按设备、视频流、规则和时间筛选；可标记
  已确认或误报，最近一次操作有撤销条；批量模式用于清积压；筛选结果可导出 CSV。
- **规则**——边界直接画在从检测器取回的实时画面上，画在哪就是哪。规则修改带版本号。
- **设备**——哪些检测器在线、各自的检测速率，以及每台是走硬解还是 CPU 解码。

告警同时回发到 MQTT，NVR、PLC 网关或你已有的告警系统可以直接订阅，不必轮询接口。

## 实测数据及其来源

下面每个数字都来自实测台架，不是规格书。

| | 结果 |
|---|---|
| 采集到告警的端到端延迟 | P50 208.7 ms，P95 392.1 ms（CPU 检测器） |
| 越线时刻与真值的偏差 | 0.009-0.25 s，方向零误报 |
| 区域进入时刻与真值的偏差 | 0.025-0.057 s |
| 滞留时长与真值的偏差 | 不超过 0.25 s |
| hub 承载两路实时流时的开销 | 单核 1.4%，常驻内存 44.9 MB |
| RK3588 检测器，int8，1280x720 | 流水线内推理 p50 41.9 ms，NPU 负载 8%，CPU 占单核 21%，硬解 |
| CPU 检测器，aarch64，1280x720 | 推理 30-37 ms，对 15 fps 源稳定跑 14.92 fps |
| int8 相对 fp16 的精度，COCO person | AP@.5:.95 掉 0.52，小目标掉 0.61 |

时刻偏差来自一段 130 s 的视频：其中每一次越线和进入区域的发生帧是已知的，通过 RTSP
回放进真实流水线后逐条比对。

## 哪些经过验证，哪些没有

已在真实硬件上验证：

- CPU / ONNX 检测器。
- RK3588 检测器，且确认它真的在用板卡硬解，而不是已经悄悄退回 CPU。
- hub——规则、冷却、告警生命周期、存储、REST 与 WebSocket 接口。
- 浏览器工作台。
- 上表中的真值断言。

未验证，也不作声称：

- **不存在 TensorRT 检测路径。**「Jetson 单机部署」套餐跑的是 CPU / ONNX 检测器，
  GPU 处于空闲。如果你现在就需要 Jetson 上的 GPU 推理，请改用
  `industrial_security_jetson`。
- **reCamera 与 Hailo 的探测节点尚未构建。** 报文契约已公开，新增它们不需要改动 hub，
  但这里没有任何在这两类硬件上运行的东西。
- **两路以上的并发容量未测。** 实测过的最大规模是两路。
- **小目标精度的结论只在 COCO 上成立。** 标定素材里几乎没有远处的人，因此广角俯拍、
  人在 30 m 外的场地超出了实测范围。正式采用前请用该场地的实拍素材重新测一遍。

## 硬件要求

| 角色 | 要求 |
|---|---|
| 摄像头 | 任意固定机位的 RTSP 摄像头。RK3588 套餐的硬解路径要求 H.264。规则画好之后摄像头不能再移动。 |
| 探测节点 | 装有 `rknpu2` 运行时和 `rknn_toolkit_lite2` 的 RK3588 板卡；或任意 arm64 / x86_64 机器，每路 720p 预留约 2.5 个 CPU 核。 |
| 汇聚主机 | 不需要。broker 和 hub 就跑在做检测的那台机器上。只有可选的「共享 Hub」套餐才需要另一台常开、装有 Docker 的 arm64 或 x86_64 机器。 |
| 网络 | 检测器要能连到 hub 的 1883 端口，值班终端要能连到 8090。摄像头预览端口 8099 必须能被值班浏览器访问，否则规则编辑器没有底图。 |

## 怎么选套餐

两个部署套餐都是单机自足：broker、hub 和检测器都在同一台机器上，部署完成后工作台就
由这台机器提供。

- **Jetson 单机部署**——一台 Jetson 看一路摄像头，用 CPU / ONNX 检测器。
- **RK3588 单机部署**——一块 RK3588 板卡看一路摄像头，推理走 NPU、解码走板载硬解。
- **共享 Hub（可选扩展）**——它本身不是一条部署路径。只有当你已经有多台检测设备在跑、
  希望它们共用一份告警列表时才用：在另一台常开机器上装 broker 和 hub，再把各台检测器
  的 `mqtt_host` 指过去。

## 开始之前值得知道的一种失效形态

检测器跟不上摄像头时，表现出来的不是"慢"，而是**误报**。帧成簇到达，相邻两次上报的
间隔超过跟踪器的容忍时间，跟踪器给同一个人发了新的编号，而这个新编号"从未进过区域"，
于是区域告警又报了一次。看上去像规则引擎坏了，其实不是。

两件事可以避免它：给检测器的推理线程数设上限，不要让一个检测器吃满整机（实测：不设
上限时 900% CPU、推理 138 ms，设上限后 250%、50 ms）；以及在怀疑规则之前，先看设备页
上的检测速率。
