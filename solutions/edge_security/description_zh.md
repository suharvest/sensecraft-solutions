## 它并入了原来那个只支持 Jetson 的方案

原本还有一个只支持 Jetson 的工业安防方案。它已于 2026-09-07 并入本方案：同一主题、
不同部署路线，做成一个方案多个套餐，不拆两个页面。它的能力落在这里的
**Jetson 单机部署**套餐上。

探测层与判定层被改写成两个进程，通过一份公开的 MQTT 报文契约通信。正因为如此，
RK3588 板卡或 Hailo 板卡可以独立跑完整套，其他探测硬件后续接入也不需要改动 hub。

**原方案有什么，现在在哪**

| 原方案的能力 | 在本方案的位置 |
|---|---|
| Jetson Orin 上的 TensorRT FP16 人员检测 | Jetson 单机部署套餐——TensorRT 10.3.0 跑 YOLOv8n，Orin NX 16GB 实测单次推理 4.13 ms |
| GPU 视频硬解（NVDEC） | 同一套餐，已在内核层核实；`require_hw_decode` 打开，主机不支持时预检直接失败，而不是降速运行 |
| 禁区入侵、越线、滞留 | 三条都在，越线可设方向，滞留告警叠加在入侵告警之上而不是替代它 |
| 浏览器看板、在实时画面上画规则 | 告警工作台与规则编辑器，底图由 hub 从检测器代理而来 |
| 事件持久化，重启不丢 | hub 的告警库，每条带截图，支持 CSV 导出 |
| 一台机器接多路摄像头 | 一路摄像头一个检测器容器，多个检测器汇入同一个 hub——而且这些检测器不必是同型硬件 |
| Orin NX 16GB 与 Orin Nano 8GB | 都在，即 `recomputer_j40` 与 `recomputer_j30` |

**多出来的能力**：告警现在也从 MQTT 发出去，NVR 或 PLC 可以直接订阅而不必轮询；
判定层可以跑在与检测器不同的机器上。

**原来丢掉的四项浏览器功能，现在补回来了。** 原方案是一个进程带一块视频墙看板；
本方案拆成检测层 + hub，要在这条分界上重建这四项，得先给契约补一条控制通道：

| 原看板能做的 | 本方案 |
|---|---|
| 自适应网格，把每路摄像头的标注画面放在一页 | **已恢复。** 工作台里有视频墙：1/2/4/6/9 格，每格叠检测框和该路的禁区、越线 |
| HDMI 全屏模式，按 F 切换 | **已恢复。** `F` 进出全屏，`Esc` 退出 |
| 在看板上调检测置信度 | **已恢复，且按路独立。** 每格一个滑块，直接下发到运行中的检测器——不用重启——同时写回 `config/detector.yaml`，重启后也还在 |
| 运行中从看板的摄像头管理面板动态加一路摄像头 | **已恢复。** 对话框里填 RTSP 地址和名称，检测器挂上这路流，画面即刻出现在墙上。一个检测器进程现在可以带多路摄像头 |
| 主面板上持续的标注视频 | **以格子的形式恢复，不走代理。** 每格直接嵌该路自己的实时地址，由浏览器去取；hub 只出叠框 JSON |

有一处与原看板不同，是有意为之，估算部署规模前值得知道：**视频不经过 hub。**
原方案自己吐标注 MJPEG，每多一个观看者就多一路流；这里浏览器直接对着摄像头侧取流，
所以不管几个人看，hub 的开销都是每秒几个 JSON 请求——代价是浏览器要能访问到检测器
自己的地址，在做了网段隔离的现场，这条路由是原来的单机方案不需要的。

另一处不同是失败时怎么说。经 MQTT 把设置推给检测器会超时，而超时既不是失败也不是
成功：对话框不关，明说结果未知，不会把自己画成"已生效"。

**有一组数字没有沿用。** 原方案宣传 YOLO26n「约 268 QPS、约 3.7 ms」和
「Orin NX 上 30+ FPS」，但没有写明测试平台与素材。这些数字在本方案里没有复现过，
因此不进下面的表。表里每一行都写明了实测所用的板卡。

### 旧 id 与它留下的空窗

两个方案不共用数据存储，因此不存在迁移路径；已经在跑的部署在重新部署之前不受影响。

旧 id **不是**本方案的别名。`solution.yaml` 里的 `replaces:` 不是 spec 定义的字段——
`spec/solution.schema.json` 里没有它，`packages/` 下的模型里也没有，加载时会被静默丢弃，
解析不出任何东西。留着它只是把「这个包去哪了」写进文件里。旧 id 登记在
`solutions/.deprecated.json`，manifest 生成脚本会把它拷进 manifest 的 `deprecated`
数组；那是标记为已废弃，不是做跳转。

所以任何还拿着 `industrial_security_jetson` 的东西——书签、外链、写死的部署引用——
从目录被删那一刻起就会拿到 404，直到消费 manifest 的那一侧改指 `edge_security`。
这个空窗是真实存在的，本方案里没有任何东西能把它补上。

### 发布顺序

这次合并要按顺序发，否则中间会出现一段谁都打不开的时间：

1. 先把承接方 `edge_security` 在 hub 的 `content/reference-designs/registry.yaml`
   里从 `review` 改成 `live`，让它的页面先存在。
2. 再合并上游这个删除旧包的 PR。
3. 然后跑一次 `prune-stale-typesense`，把旧 id 的孤儿文档清掉。

顺序反了——先删包再放行 `edge_security`——旧页面已经 404，新页面还没上线，
指向工业安防的入口在这段时间里全是断的。

## 这个方案做什么

摄像头看现场，边缘盒子在画面里找人，一台 hub 把结果判成三类告警，汇成一份可以逐条
处理的列表：

- **禁区入侵**——有人进入你在画面上画出的多边形。
- **越线**——有人跨过一条线。规则可以限定方向，因此"进院"和"出院"是两条不同的告警。
- **区域滞留**——有人在区域内停留超过你设定的时长，在入侵告警之外再出一条，而不是
  替换它。

探测层和判定层是两个进程，通过 MQTT 通信。这也是它区别于单摄像头演示的地方：一台 hub
可以带多台不同种类、装在不同房间的检测器，值班人员只看一份告警列表。

## 值班人员实际看到什么

hub 自带的浏览器工作台，中英文均可：

- **工作台**——告警列表，每条带现场快照；可按设备、视频流、规则和时间筛选；可标记
  已确认或误报，最近一次操作有撤销条；批量模式用于清积压；筛选结果可导出 CSV。
- **规则**——边界直接画在从检测器取回的实时画面上，画在哪就是哪。规则修改带版本号。
- **设备**——哪些检测器在线、各自的检测速率，以及每台是走硬解还是 CPU 解码。

告警同时回发到 MQTT，NVR、PLC 网关或你已有的告警系统可以直接订阅，不必轮询接口。

### Hub

实测在同时还跑着检测器的 RK3588 板卡上占**单核 3.7%、RSS 52.8 MB**。Orin NX 上没有单独取过这个数。
这就是每个套餐都把 hub 放在检测机器上、而不是另要一台机器的原因。

### 精度

**RK3588 上 int8 相对 fp16，COCO person：AP@.5:.95 掉 0.52，小目标掉 0.61。** 该平台
默认用 int8，因为流水线内快 42%，代价就是这个。Jetson 走 FP16，不存在量化损失。

## 一台 Jetson 能带几路摄像头

下面这些决定性数据都测自 Orin NX 16GB。

- **GPU 上限：236 次推理/秒**（所有上下文合计）。工作进程满负荷跑：1 个 → 166.7/s，
  2 个 → 231.2/s，4 个 → 237.0/s，8 个 → 235.8/s。从两个进程起总吞吐就不再增长，
  说明 GPU 是共享瓶颈，饱和点就在这里。
- **每多一个检测器进程多占 208 MB 统一内存**，各自持有自己的 engine、context 和 Python
  运行时。系统已用内存：基线 3977 MB → 1/2/3/4 个进程时 4172／4394／4600／4822 MB。
- **在真实速率下互不干扰。** 四个进程各自以 5 fps 推理，实测 p50 分别为 4.02／4.07／
  4.04／4.02 ms，与单进程独跑没有区别。

| 路数（1080p @ 15 fps） | 做法 |
|---|---|
| **1 – 8 路** | 一路摄像头起一个检测器容器，不需要写任何新代码。8 路占板卡 15.6 GB 中的 1.7 GB，120 次推理/秒对 236 的上限约 51% GPU，单帧延迟仍停在空载水平，不会进入排队区间。 |
| **8 – 16 路** | 改用动态 batch 的 engine，前提是有人先把批量吞吐实测出来。批量能摊薄每次推理 1.21 ms 的 enqueue 开销，但一个 batch 必须等最慢的那一路交出帧才能下发，每条告警最多要多等 67 ms。 |
| **16 路以上、4K，或需要拼接大屏** | 上 DeepStream。超过 16 路后 CPU 侧的预处理才真的成为瓶颈，只有 NVMM 零拷贝能绕开。另外 JetPack 6.1 版的 DeepStream 7.x 装完要 1.5–2 GB 磁盘，并且把你锁死在一组 JetPack／`pyds` 版本上。 |

上表里有两个输入是外推的、不是实测，谁要按 8 路规格卖机器之前应当在目标分辨率上核实：

- **1080p 15 fps 下每路的 CPU 占用。** 由 720p 5 fps 实测的单核 8.5–12.5% 线性外推，
  约每路 0.5–0.7 个核，8 路约占 8 个核里的 4–5 个。**需核实。**
- **NVDEC 并发 8 路 1080p15 的会话容量。** Orin NX 解码器的总像素率规格远高于此，
  但这里的所有测量都只用了一路。**需核实。**

## 哪些经过验证，哪些没有

已在真实硬件上验证：

- Jetson TensorRT 检测器，在一台 Orin NX 16GB 上，且确认它真的在用 NVDEC 硬解——
  容器进程持有 `/dev/v4l2-nvdec`，协商出的 caps 带 NVMM 来源标记——而不是已经悄悄
  退回 CPU。
- RK3588 检测器，同样做了针对板卡硬解的确认。
- 两个套餐都以容器形式完整部署过，用的就是这里随方案下发的 compose 文件与部署步骤。
- hub——规则、冷却、告警生命周期、存储、REST 与 WebSocket 接口。
- 浏览器工作台。
- 上表中的真值断言。

**broker 接受匿名连接，但只有「共享 Hub」套餐会把它暴露出去。** 每个套餐的 mosquitto
都是 `allow_anonymous true`。三个单机套餐里它绑在 loopback 上——检测器和 hub 走 compose
内部网络连它，局域网上没有任何东西能往里发消息。「共享 Hub」套餐是有意的例外:远程检测器
必须能连到 1883，所以那一个监听在网络上，任何能连到该端口的机器都可以往检测主题发消息
——包括伪造的检测结果和判定事件，而安防工作台会把它们当成真告警显示。把那台主机放到管理网
或摄像头 VLAN，并在 `assets/hub/config/mosquitto.conf` 里加 `password_file`、在各检测器
配置里配上对应凭据。如果你为了接第二台检测器而把某个单机套餐的 broker 重新发布到局域网，
同样适用:改端口绑定的同时要加密码文件，不能只做前一半。8090 上的工作台不受影响，它需要登录。

未验证，也不作声称：

- **reCamera 的探测节点尚未构建。** 报文契约已公开，新增它不需要改动 hub，但这里没有
  任何在这类硬件上运行的东西。Hailo 的探测节点已构建并实测，见 Hailo 套餐。
- **两路以上的端到端并发未测。** 上面的多路数据是用工作进程测的 GPU 与内存开销，
  不是八台摄像头配八套规则跑出来的。
- **小目标精度的结论只在 COCO 上成立。** 标定素材里几乎没有远处的人，因此广角俯拍、
  人在 30 m 外的场地超出了实测范围。正式采用前请用该场地的实拍素材重新测一遍。

## 硬件要求

| 角色 | 要求 |
|---|---|
| 摄像头 | 任意固定机位的 RTSP 摄像头。必须是 H.264——Jetson 与 RK3588 套餐走硬解，Hailo 套餐走 CPU 软解（Pi 5 没有 H.264 硬解）。规则画好之后摄像头不能再移动。 |
| 探测节点 | 一台 JetPack 6.x 的 Jetson Orin（Orin Nano 8GB 或 Orin NX 16GB），装有 TensorRT 与 nvidia 容器运行时；**或者**一块装有 `rknpu2` 运行时和 `rknn_toolkit_lite2` 的 RK3588 板卡；**或者**一台 PCIe 插槽上装了 Hailo-8、并装好驱动与版本匹配 HailoRT 的 Raspberry Pi 5。 |
| 汇聚主机 | 不需要。broker 和 hub 就跑在做检测的那台机器上。只有可选的「共享 Hub」套餐才需要另一台常开、装有 Docker 的 arm64 或 x86_64 机器。 |
| 磁盘 | Jetson 与 RK3588 套餐在检测机器上约需 6 GB 空闲：检测器镜像、hub 镜像、在本机构建的 TensorRT 引擎，以及告警数据库。Hailo 套餐约需 4 GB，它不构建引擎。 |
| 网络 | 检测器要能连到 hub 的 1883 端口，值班终端要能连到 8090。摄像头预览端口 8099 必须能被值班浏览器访问，否则规则编辑器没有底图。**1883 上的 broker 接受匿名连接**——放到通用网络之前先看下面那条说明。 |

## 怎么选套餐

三个部署套餐都是单机自足：broker、hub 和检测器都在同一台机器上，部署完成后工作台就
由这台机器提供。

- **Jetson 单机部署**——一台 Jetson Orin 看一路摄像头，推理走 TensorRT、解码走 NVDEC。
  引擎在部署过程中于本机构建，首次安装因此多花约五分钟。
- **RK3588 单机部署**——一块 RK3588 板卡看一路摄像头，推理走 NPU、解码走板载硬解。
- **Hailo 单机部署**——一台装了 Hailo-8 的 Raspberry Pi 5 看一路摄像头，推理走加速器。
  解码在 CPU 上，这是主路径而不是降级：该板卡没有 H.264 硬解，所以检测器的 CPU 占用里
  同时包含解码和推理。
- **共享 Hub（可选扩展）**——它本身不是一条部署路径。只有当你已经有多台检测设备在跑、
  希望它们共用一份告警列表时才用：在另一台常开机器上装 broker 和 hub，再把各台检测器
  的 `mqtt_host` 指过去。

## 开始之前值得知道的一种失效形态

检测器跟不上摄像头时，表现出来的不是"慢"，而是**误报**。帧成簇到达，相邻两次上报的
间隔超过跟踪器的容忍时间，跟踪器给同一个人发了新的编号，而这个新编号"从未进过区域"，
于是区域告警又报了一次。看上去像规则引擎坏了，其实不是。

单路摄像头下两个套餐都离这个边界很远——Jetson 检测器在 200 ms 的帧周期里只花 7.24 ms，
RK3588 是 44.3 ms——但如果你往一台机器上接太多路摄像头，或在旁边跑别的重负载，最先
出现的就是这个现象。怀疑规则之前，先看设备页上的检测速率。
