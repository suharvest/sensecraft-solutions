## 这个方案能帮你做什么

这套方案把出入库操作变成说话：说"入库 20 件"，系统记录；说"A3 还有多少货"，系统回答。工人在作业位置就能录入，不必走到电脑前，也不必事后凭记忆补录。

## 核心价值

| 好处 | 具体说明 |
|------|--------|
| 零学习成本 | 不用培训，不用记菜单，开口说话就能操作 |
| 作业不中断 | 语音完成出入库和查询，手不停，人不动 |
| 库存实时准确 | 操作即记录，没有补录，没有延迟 |
| 减少人为差错 | 不经手工录入，漏录、错录从源头减少 |
| 无需换系统 | 已有ERP/WMS直接对接，没有系统用内置的 |

## 适用场景

| 场景 | 怎么用 |
|------|--------|
| 收货入库 | 说"入库 5 台 Watcher"，系统自动登记，货放下就完事 |
| 拣货出库 | 说"出库 3 台发给某某公司"，自动生成出库单 |
| 盘点核对 | 说"今天入了多少货"，语音汇总当日数据 |
| 叉车作业 | 司机说"A3 货架还有多少货"，语音播报库存数量，不用下车 |

## 使用须知

### 系统对接方式

- 接入现有 ERP/WMS：通过数据接口桥接，需补充约几十行数据映射代码
- 直接用现成系统：平台自带仓管系统，零额外代码
- 两种均支持

### 语音特性

- 支持模糊指令识别，自动匹配最接近的命令
- 指令库可扩展

## 实测边界

下表数字来自 2026-09-05 与 2026-09-06 在 **开发板基准（更快的 arm64 开发板，非套餐设备，SoC 也不同于 R1100 的 CM4 级）** 上的压测，用的是按 digest 锁定的 arm64 镜像与 SQLite 后端。这些数字不构成对其他设备、更大数据量或 MySQL 后端的吞吐承诺。

| 仓库能得到什么 | 典型值 | 设备 |
|---|---|---|
| 10 个人同时查库存时的响应 | **p95 404 ms**，错误率 0% | 开发板基准 |
| 入库记录写入 | **p95 106 ms**，错误率 0% | 开发板基准 |
| 并发入库产生的错单与重单 | 1481 个批次里 **0 个** | 开发板基准 |
| 服务中断 34 秒后恢复 | **约 1 秒**，无积压、无脏数据 | 开发板基准 |
| 角色与租户隔离 | **4/4** 符合预期 | 开发板基准 |

口径：Mac 客户端经 Tailscale，每个请求都走真实 WAN 跳数，每档 60 秒，50 个种子物料，1 个仓库，SQLite。查询时延随同时在用的人数增长：并发 20 时 p95 翻倍到 824 ms，并发 50 时到 5.5 秒，已不可用。出库在默认 600 次/分钟阈值下，单个 API Key 的持续吞吐约 5–6 次/秒，限流按已认证身份计数。

2026-09-07 用同一枚 digest 的镜像部署到 **reComputer R1000 同款 CM4 平台**，跑在开发板上而非 R1000 整机，因此是平台参考值，不是整机实测。本方案内存需求为 4 GB 起步，选购 R1000 时选 4 GB 或 8 GB 配置。该轮只覆盖重启恢复：容器 restart 到服务健康分别为 9.48 秒 与 9.04 秒。上表的负载数字尚未在该平台复现，待 4 GB / 8 GB R1000 上跑完后补充。

## 数字的适用范围

- **仓储 REST 接口压测**——一次压测运行，2026-09-05，跑在一块更快的 arm64 开发板上（SoC 不同于 R1100 的 CM4 级），50 个物料，SQLite，每个并发档位 60 s，客户端经 Tailscale。
- **修复后的并发与限流行为**——同一台设备复测，2026-09-06。
- **Jetson 上的本地 LLM 吞吐**——reComputer Robotics J5011 上约 16 tokens/秒，上游给出的数字，没有附运行日志。
- **识别准确率、唤醒拾音距离与端到端语音时延**——请在自己的现场实测。

## 已知限制

- **并发入库用延迟换正确性。** 批次号由原子计数器分配，对同一物料的写入会串行。并发上升体现为 p95 上升，不会产生冲突，批次号始终唯一。业务繁忙的现场请增加仓库或把入库分散到多个物料，而不是提高单物料并发。
- **出库按已认证身份限流。** 阈值是 「BUSINESS_RATE_LIMIT」，默认每分钟 600 次，按 API Key 或会话计数——同一 NAT 后的多台终端不共用配额。注册、找回密码、设备校验的防枚举限速仍按来源 IP 计数。单个 Key 的持续请求要超过每秒 10 次时，先调高阈值。
- **REST 层没有离线队列。** 网络或服务中断期间发出的请求直接失败，恢复后不会补发；重连与退避逻辑只覆盖 MCP 语音 WebSocket 通道，不覆盖 HTTP 库存接口。实测 34 s 中断期间 100% 请求失败，恢复后无积压、无脏数据。**规避方式二选一**：一是在网关侧保证网络可用性（有线优先、UPS 供电、把服务与客户端放在同一局域网内，避免中断跨越广域网），把不可用窗口压到设备重启时间；二是在客户端做写入队列——出入库请求先落本地，联通后按顺序补发并按批次号去重；该队列本包不含。
