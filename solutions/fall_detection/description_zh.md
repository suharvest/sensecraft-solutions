## 这个方案做什么

把摄像头变成一个会报「有人摔倒了」的传感器。摄像头盯住一块固定的室内区域，在
设备本地判断有没有人倒地，然后把事件推给你已经在用的系统——Home Assistant、
护理呼叫系统、NVR，或者你自己的服务。

除非你主动去看，视频不出设备。姿态估计、跌倒判定和事件状态都在本地完成，网络上
传的只是一条很小的 JSON 消息。

## 你会得到什么

**一条跌倒事件流。** 每个人被单独跟踪，编号在他走动时保持不变；状态依次经过正常、
疑似、已跌倒、恢复中。「这是一次新的跌倒」只在状态跳变的那一刻触发一次，所以自动化
可以只响应一次，而不是在人躺着的整段时间里反复触发。字段名见下方接口表。

**开箱可用的 Home Assistant 实体。** 两个套餐都会发 MQTT 自动发现配置，跌倒传感
器、当前状态、事件编号和有人存在传感器会自动出现在 Home Assistant 里，不用手写
YAML。

**一个可选的告警面板。** 事件流本身只是一条数据流。面板把它变成有人负责的告警：
房间、摄像头与识别区域的站点总览与 24 小时告警趋势；在每路摄像头的实时画面上直接画
识别区域；每个区域各自的无人超时与静止超时；取证窗口；由值班人确认、驳回或标记已处置；
SQLite 审计链；以及一条不携带任何视频的 webhook。在 reComputer J30 / J40、RK、R2000 三个套餐里
它是同一份 compose 里的一个服务；在两个 reCamera 套餐里它是可选的一台额外主机。
下面的「告警面板」一节说明它做什么。

**一个用于现场调试的实时画面。** 部署的最后一步会在本应用里打开预览：视频上叠加
骨架、每个人的状态和证据计数，让你在接通知流程之前先确认摄像头确实看得到该看的
东西。

## 适合接到哪里

- **养老与居家照护**——无人看管的卫生间、走廊、卧室，摔倒后可能直到下一次查房才
  被发现。
- **已有的摄像头**——reComputer 套餐直接接入标准 RTSP，手上现成的摄像头不用换就能
  加上跌倒检测。
- **Home Assistant 自动化**——一个跌倒实体，可以拿来开灯、推送通知或发起呼叫。

## 实际效果如何

以下是公开数据集上的工程基准，**不是医疗或人身安全认证**。GMDCSA-24 v2.1 按人切分：
Subject 1–2 用于训练时序模型，Subject 3 用于选阈值并冻结配置，Subject 4 作为留出测试集
只读一次——27 段片子（12 段跌倒 / 15 段日常动作），15 FPS。

| 现场能得到什么 | 典型值 | 设备 |
|---|---|---|
| 跌倒到告警 | 平均 **1.61 秒** | reComputer R2000（Hailo-8） |
| 跌倒召回，冻结时序门 | **100%** | 同一主机，27 段留出集 |
| 日常动作不误报 | **80%** | 同一主机与数据集 |
| 15 FPS 下一台主机同时接几路（测试时关闭 MQTT） | **16 路** | reComputer R2000（Hailo-8） |
| 接入告警面板后，跌倒到告警送达 | **P50 2.83 秒** | reComputer R2000（Hailo-8），确认窗口已调短 |

各冻结平台配置的准确率落在 74.1% 到 88.9% 之间，平均告警时延落在 1.22 秒 到 1.75 秒 之间，
所以**选硬件看路数，不看准确率**。路数随主机变化：reCamera Pro 与 reComputer RK3576 各 1 路、
reComputer RK3588 5 路、reComputer J30 8 路、reComputer J40 9 路、选配 Hailo-8 的
reComputer R2000 16 路。这些是用真实 640×640 H.264 / 15 FPS 源测到的最高负载，
是自行压测的起点而不是标称能力。

面板那一行是整链——摄像头到检测器到面板再到 webhook，取证窗口调到 1 秒、自动确认窗口
调到 1 秒。用出厂默认值（5 秒 + 60 秒）时同一条链路要一分钟出头，这是确认机制本身，
不是额外开销。面板的通知器还会在每 10 分钟发满 5 条后停止发送。

RK 与 Hailo 两行量的是冻结时序门，不是部署态完整状态机的精度；Hailo 那轮容量测试
期间关掉了 MQTT。留出集只有 27 段，因此一段片子就会让指标动 3.7 个百分点。
结果冻结于 2026-09-05。

换到独立外部数据集（RealBiomFall，34 段纯跌倒片段），召回降到 52.9%–58.8%。制约因素是
姿态覆盖：远景与重遮挡下人几乎检不出来。上表覆盖的是取景良好的室内中近距离视角。
## 输出接口

| 输出 | 位置 | 内容 |
|---|---|---|
| 跌倒结果 | MQTT 1883 端口，主题 「<设备名>/fall-detection/results」（多路套餐为 「.../results/<流编号>」） | 每帧一条 JSON：整体状态加每个被跟踪者一条记录 |
| 在线状态 | MQTT 1883 端口，主题 「<设备名>/fall-detection/status」 | 「online」 / 「offline」，retained |
| Home Assistant | 「homeassistant/」 下的 MQTT 自动发现 | 跌倒传感器、状态、事件编号、人数 |
| 视频 | reCamera 的 RTSP 8554 端口 「/live0」，或你自己的 IP 摄像头 | 检测器正在看的画面 |
| 告警列表与操作 | HTTP 8080 端口，「/api/alarms」 与根路径页面——仅告警面板 | 告警记录，含状态、区域、流编号、时间戳与操作者；确认、驳回、标记已处置 |
| 通知 | HTTP POST 到你的 webhook 地址——仅告警面板 | 告警 id、类型、区域、流、时间戳、操作者，另带幂等头——不含快照和视频 |
| 告警总线（可选，默认关闭） | MQTT 1883 端口，主题 「eldercare/alarm/<区域 id>」——仅告警面板 | 与 webhook 相同的负载 |

**「<设备名>」 是你自己取的**，在部署步骤里作为「设备名称」填写，默认 reCamera 套餐为
「recamera」、reComputer 套餐为 「recomputer」。它只是主题的第一段，用来区分同一个 broker 上的
多台设备——按房间、楼层或站点命名都可以。「stream_id」 同时写在 payload 里，下游不必靠解析主题来判断来源。

reComputer 套餐可以用一台设备接入多路摄像头，并把流编号拼在主题后面
（「recamera/fall-detection/results/cam-01」），下游能把每路分开处理。本方案端到端
部署预设配的是单路；15 FPS 多路容量另行实测：Orin Nano Super 8 路、Orin NX Super 9 路、
RK3576 1 路、RK3588 5 路，Hailo YOLOv8s 为 16 路、YOLOv8m 为 5 路（见性能一节）。
这些实测每路用的是同一段循环片源，
所以正式定路数前仍要用你自己的摄像头、编码和场景人数跑一遍。

## 方案对比

**reCamera 2002** 是一体化的——摄像头、推理、MQTT 都在一个装上通电就能用的设备
里。单个房间、想最快跑通一条告警链路，选它。

**IP 摄像头 + reComputer J30 / J40** 保留你现有的摄像头，把检测器放到 Jetson Orin 上，
一台同时接入多路，用更大的姿态模型换更高的实测准确率。摄像头已经有了、需要多个
视角，或者在意上面那张表里的准确率差距时，选它。

**reComputer RK3576 / RK3588** 把检测器放到瑞芯微 NPU 板卡上，带有板卡专属的时序权重和硬件视频
解码。最佳性能测试配置使用 YOLOv8s INT8，RK3576 验证 1×15 FPS，RK3588 验证
5×15 FPS；当前部署仍保留原有单相机 YOLO11n FP16 配置。

**reComputer R2000（Hailo）** 在 Hailo-8 上跑原生 C++ 热路径。默认 S 模型实测可带 16 路
15 FPS，官方 M 模型在运行时自动切换 shared batch 后可带 5 路。当前部署表单仍配置单路。
已经安装这类硬件时可以选它；时序门限已经冻结。

**告警面板跑在哪里因套餐而异。** reComputer J30 / J40、RK、R2000 三个套餐里它是与检测器同一份
compose 里的服务，由同一个部署步骤拉起，在该设备的 8080 端口打开。reCamera 2002 与
reCamera Pro 上摄像头承载不了它——那里的检测器是原生进程或应用中心应用，摄像头没有
可用的文件系统、SQLite 和 Web 服务——所以面板是一个可选的额外步骤，装到一台不需要
AI 算力的独立机器上：reComputer R1000 系列，或者你已有的一台机器。跳过这一步，摄像头
的行为与之前完全一样，只发 MQTT 事件。

## 告警面板

**站点总览，而不只是一张列表。** 首页统计房间、摄像头与识别区域数量，画出 24 小时按类型
分色的告警趋势，并给每个房间一张卡片，带自己的画面缩略图与未处置数。摄像头连不上的
房间显示为「未知 + 断流」并给出最近一帧的时间，而不是显示「正常」。

**在实时画面上画识别区域。** 区域矩形是在浏览器里、在摄像头自己的 WebRTC 画面上画出来的，
不是手填坐标。坐标按画面而不是按容器映射，所以 4:3 的画面放进 16:9 的框里时，两侧黑边
留在矩形之外。保存会让配置版本加一并在变更记录里多一行；如果另一位管理员先保存了，
本页会拿到 409 与「重新载入」提示，而不是静默覆盖对方的改动。

**每个区域三类告警。** 跌倒来自检测器的事件。区域无人与人静止不动由面板自己判定，
依据是 「person_count」 与每个被跟踪者边界框中心的位移。每个区域各有自己的
「no_person_timeout」 与 「no_motion_timeout」——卫生间和卧室不是同一个问题。

**多一道人工确认，而不只是推送。** 告警先进入 5 秒取证窗口，再等待值班人 60 秒。
确认与驳回都会记下按下它的人。窗口内无人应答时，默认按真实告警处理并通知——可以通过
「statemachine.confirm_timeout_action」 改成相反行为。

**可审计的送达。** 已确认的告警必须在 5 秒内完成通知，否则转入 「escalated」 并停在
那里，每 30 秒重试一次。即使某次重试成功，「escalated」 也不会退回 「notified」，
审计链因此能看出期限被错过。每条通知带幂等键
（「zone:kind:event_timestamp:global_event_id」），告警表与通知表都对它建了唯一索引——
重放和重试不会产生重复告警或重复送达。一次实测的断网恢复里，排队的 3 条全部送达、
无重复，第一条在端点恢复后 96 毫秒发出。

**通知里没有视频。** 负载是告警 id、类型、区域、流编号、时间戳与操作者。没有快照，
没有片段。快照采集只是一个配置开关（「web.snapshot_enabled」），默认关闭，后面也还
没有实现。

**默认全本地。** 整条链路不依赖云。事件、状态跃迁、操作者与送达回执保留 90 天；
媒体文件若启用则保留 7 天，每天清理一次。

**面板不是医疗器械，也不是通过认证的紧急救援产品。** 它不做诊断、不做治疗，也不替代
照护者的判断。告警只是一个提示，判断和响应仍然由人来做。

### 语音确认（可选）

默认关闭，关闭时对方案其余部分没有任何影响。打开后，一条跌倒告警会让面板向房间播报
提示——「您还好吗？请回答」——并听取几秒钟，与 5 秒取证窗口并行，而不是排在它后面。

呼救、完全没有回答、或者听不懂的回答，都会立即确认该告警并跳过剩余的人工窗口。
「我没事」默认**不会**关闭告警：它把告警标记为待复核，并让正常计时继续。想让它直接
关闭，把 「on_ok」 设为 「dismiss」。这种不对称是有意的——听错一句「我没事」会压掉一次
真实跌倒，而一次没必要的确认只花值班人几秒钟。同理，同一句话里出现求救词就压过安全词，
关键词表认不出来的说法按确认处理而不是等待。

音频硬件是接在跑面板那台机器上的 USB 麦克风与扬声器，另需一个 OpenVoiceStream 实例
提供 TTS 与流式 ASR。摄像头不承担音频通路：两款 reCamera 都没有确认可用的麦克风，
SG2002 也完全跑不了本地 ASR。TTS 与 ASR 会和检测器抢同一台机器的 CPU、加速器与内存——
一次只跑一个会话、提示音预先合成、OVS 超时一律按确认处理，是这套设计用来避免这种争抢
代价落到告警上的手段。

**隐私。** 音频不落盘。原始 PCM 只在一次听取窗口内驻留内存，判定产出后即释放。落库的
是判定结论、置信度、时延与转写文本；把 「store_transcript」 设为 「false」 则连文本也
不留，审计链里只剩判定结论。通知会多带这几个字段，仍然不含快照和视频。

## 使用须知

- **构图决定准确率。** 上面的数字来自固定机位、近中景、肩部和髋部可见的室内画面。
  垂直俯拍、长走廊远景或家具严重遮挡的场景表现会更差。

  ![机位示意：2–3 m 的侧向或斜角机位可用；垂直俯拍、远景和被遮挡的机位不可用。](https://files.seeedstudio.com/Solution/landpage_asset/fall-detection/camera-placement-be3fb598.svg)
- **跌倒过程必须发生在画面里。** 如果启动时人已经躺着，它会报告姿态但不产生事件。
- **MQTT broker 因套餐而异。** reCamera 2002 自带本地 broker；reCamera Pro 不带，接 MQTT 要指向外部 broker，不接则在设备自带页面看结果；
  reComputer 套餐会随检测器一起启动一个。
- **识别区域是画面上的归一化矩形。** 移动或重新对准摄像头会让区域划分失效，而且不会
  报任何错——矩形还在，只是覆盖到了房间的另一块地方。任何物理改动之后都要重新核对区域。
- **睡眠时段会触发「静止超时」**，除非区域排除床位，或者阈值长于一次正常午睡。这里的
  「运动」指被跟踪者边界框中心的位移超过 「motion_threshold」（默认 0.02 归一化值），
  不是光流也不是关键点速度——被子下的小幅动作不算。
- **无人超时依赖检测器发送空帧。** 画面里没人时就什么都不发的检测器，会让这个超时收不到
  输入。Jetson 的配置里 「publish_empty_frames」 已经是 true；Hailo 运行时没有这个开关也
  不需要。RK 板卡上如果跌倒能告警而无人告警从不触发，先确认画面里没人时检测器仍在发消息。
- **遮挡会造成一次误报的「无人」。** 区域只在人再次被看到之后才重新布防，所以一次遮挡
  产生一条告警而不是一串——但它确实会产生一条。
- **面板里的 Telegram 与邮件只是接口占位。** 选中它们会抛错并落进重试队列，而不是把通知
  静默丢掉——这是设计意图，但它们不是可用的通道。
- **reCamera 同一时间只能跑一个视觉应用。** 安装会把摄像头从 Node-RED 和其他视觉
  应用手里接管过来。
- **表中的延迟是检测延迟**——从标注的跌倒起点到告警发出，在离线评测环境中测得。
  姿态引擎单独给出的 FPS 数字则只代表推理内核部分。
