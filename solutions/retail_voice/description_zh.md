## 这套参考设计是什么

一只 reSpeaker XVF3800 麦克风阵列把一路 16 kHz 单声道音频送进门店里的边缘盒子，盒子把门店对话转成文字。文字之后怎么处理，是这套设计交给你选的：可以就以文件形式留在盒子上，也可以走一套服务端栈——入库前脱敏，并且能按主体硬删除、还能证明删干净了。

两条路用的是同一套采集硬件和同一个语音服务。它们是同一套设计的两个套餐，不是两个产品。

## 两种部署方式

**设备本地转写**——一台盒子、一只麦克风、一个转写目录。采集、端点检测、转写、标点恢复和可选的声纹匹配都在同一块板上完成。没有云端账号，不上传，没有数据库；镜像和模型就位之后不需要对外连接。单店或试点门店、不希望录音离开现场、本地文本文件本身就是可接受产物时选它。

**服务端栈**——一台主机跑完整链路：ASR 端点、声纹、入库前脱敏的服务、MySQL、MinIO，以及带导出和硬删除的管理后台。音频来自你已有的手机 App、来自边缘采集端上的麦克风阵列，或两者都有。当有人会提出「把我的数据删掉」、而「行还在、状态位改了」不是可接受的答复时选它；或者多个站点需要一份可查询的记录时选它。

| | 设备本地转写 | 服务端栈 |
|---|---|---|
| 产出 | 设备上的 JSON 文件 | MySQL 里的脱敏记录、MinIO 里的音频、3000 端口的后台 |
| 采集 | 盒子上的 reSpeaker XVF3800 | 同一只阵列，或你的手机 App 经 ASR 端点上传 |
| 脱敏 | 没有——文字就是说的内容 | 入库前替换成带类型的占位符，原文从不写入 |
| 删除 | 你自己针对目录写的脚本 | `POST /api/v1/privacy/erase`，级联三处存储，带残留数 |
| 板卡 | reRouter CM4（CPU）或 reComputer RK3576（NPU） | reComputer RK3576，或其他 arm64 Linux 主机 |
| 部署耗时 | 约 40 分钟 | 约 60 分钟 |

采集侧完全一致，所以从本地套餐起步的站点之后要换到服务端栈，麦克风、板子和识别器都不用换。

音频怎么进到服务端栈：

```
  手机 App（你自己的，不在本包内）
        │  WebSocket，16 kHz 单声道 PCM
        ▼
  ASR 端点  ws://<主机>:8080/ws?token=<operator>
        │
        │            边缘采集端（reSpeaker XVF3800 + reRouter CM4 / RK3576）
        │            │  本地采音、VAD、OpenVoiceStream 转写
        ▼            ▼
  转写 + 声纹
        │  final 文本
        ▼
  voice-service ── 脱敏 ──> MySQL（只存脱敏文本）
        │                   MinIO（原音频，受保留期约束）
        ▼
  voice-web 管理后台 ── 查询 · 导出 · 硬删除
```

手机 App 不在本包内。它已经在你那边存在，这套设计提供的是一个可以指向的端点、一个要出示的令牌，以及一份写清楚的音频格式约定。

## 你会得到什么

- **需要的话，可以是单机闭环。** 本地套餐上拔掉网线，转写照常进行。转写结果写进你指定的目录；音频是否保留是一个开关——可以留下 WAV 片段，也可以只留文字。
- **脱敏发生在入库之前，不是之后。** 服务端栈套餐上，手机号、身份证号、姓名、地址在写进数据库的路上被替换成带类型的占位符（「[[PHONE]]」、「[[NAME]]」）。原文从不写入——不是加密存，是不存。关键词匹配跑在脱敏后的文本上，所以关键词表里存的也是脱敏后的文本。
- **带残留数的硬删除。** 一次调用按主体、设备或会话删除，级联清掉数据库行、MinIO 里的对象和声纹，顺序是先对象后行——先删行就再也拿不到对象路径了。留下的是一条墓碑，里面只有主体的 SHA-256，没有原值。
- **按主体导出。** 脱敏文本 JSON 加音频清单，用于回应访问权与可携带权请求。可逐字段机器核对、必须限定范围，没有「导出全部」。
- **一个可以交给 App 的 ASR 端点。** 一条 WebSocket，收原始 PCM 帧，回 JSON——连接确认、语音活动状态，以及每句话一条带说话人字段的最终转写。
- **不依赖云端身份服务的说话人标签。** 语音服务每句返回一个 192 维 CAM++ 向量，与本地注册库的匹配在同一台设备上完成，也可以整个关掉。
- **服务端栈的三档权限。** viewer 读，operator 上报，admin 删除与导出。设备拿 operator 令牌，admin 令牌留在运维手里。没配规则的路由至少要 viewer，新接口默认不是公开的。
- **占用有界、版本冻结。** compose 里限制了容器日志大小，模型放在命名卷里，栈的镜像全部按 digest 固定且没有自动更新器。云端分析是单独的 profile 且默认关闭，因为打开它会把文本发出这台机器。

## 适用场景

- 单店或试点门店，不希望录音离开现场——本地套餐，不用运维数据库。
- 上行链路不可靠的环境：地下商铺、临时柜台、厂区办公室。
- 采购规定禁止第三方处理语音，只接受本地文本文件作为产物。
- 店面里员工与顾客有对话，门店想知道被问到了什么，但不想留下是谁问的——服务端栈套餐。
- 任何需要用「真的删了」而不是「行还在、状态位改了」来回应删除请求的部署。
- 已经有手机 App 在做采集、缺后面这条链路的场景。
- 上分析之前的前置步骤：先在现场把音频通路和识别质量验证清楚，再加服务端栈。

## 实测边界

这不是经过认证的转写产品，不是合规控制手段，也不是合规认证。它产出的是下表所示质量的文本；脱敏、删除与导出的行为是代码在测试下的表现。两者是否满足某项具体法规，由部署的运营方判断，并且必须在真实安装环境里重新核一遍。在门店录音是否合法、需要给出何种告知，由你自行负责。

### 站点边界——两个套餐都适用

另有两条不是性能数字、但直接决定站点能不能用的边界：

- **背景噪声不高于 70 dB**，即正常说话的音量。超过这个水平，阵列的噪声抑制无法再把说话人从环境中分出来，词错率会在上表任何数字生效之前先劣化。
- **说话人距阵列约 3 m 以内**。这是 XVF3800 波束成形在门店里能覆盖的范围；超出后转写质量下降，与算力板型号无关。

### 隐私声明——服务端栈套餐

给这套部署写任何对外文案之前先读这一节。

- **原文转写从不落库。** 配置项存在（「privacy.store_original_text」），默认 false；打开它等于把原文放进一个删除流程还没覆盖到的地方。
- **音频没有做脱敏。** 只有文本做了。原音频在主机上按保留期存放——默认 24 小时，部署时可缩短到 6 小时或 1 小时——并被删除流程覆盖。页面绝不能写「音频已脱敏」，因为没有：v1 不做哔声与切段。
- **导出给的是清单不是音频本体**，理由同上。
- **低置信实体只标记不遮蔽。** 遮蔽阈值是 0.85 置信度，低于它的进复核队列，这就是 recall 只到 0.95 的原因。计数落在 「pii_masked_count」 与 「pii_review_count」，命中位置不落库——存下来等于把个人信息的位置又写回数据库。
- **打开 cloud-analytics profile 会把文本发出这台机器。** 文本是脱敏过的，但「内容不出场地」这句话从此不成立。

### 已知限制

- **连续说出的数字串会转写成中文数字词。** 即使 「recognition.use_inverse_text_normalization」 打开，ASR 对孤立数字串也不做逆文本正则化：一口气念出的 "13812345678" 转写结果是 "幺三八幺二三四五六七八"，不是阿拉伯数字。脱敏侧所有手机号正则都只匹配阿拉伯数字，所以在这条被处理之前，这样一条记录会带着明文号码入库、「pii_masked_count: 0」。现已补了一条 「cn_mobile_spoken」 规则，覆盖 11 位中文数字手机号形态（含报号常用的「幺」）。**仍未覆盖的：** 身份证号、座机号，以及其它以中文数字词念出的数字标识。部署方若在意这些，先用自己的录音验证，不要直接依赖脱敏；真正限制暴露面的是原音频保留期这项控制。
- **表里的脱敏分数是文本层面的分数。** 它在书面文本上测得，不是在 ASR 输出上测的。转写错误会挪动实体边界，同一条规则在干净文本上能命中的，在转写文本上可能漏掉。

**设备本地转写**

## 使用须知

### 两个套餐都适用

- **采集侧是单点。** 一台盒子、一只麦克风。设备关掉就什么都采不到。
- **声纹匹配是本地的启发式方法。** 它按固定阈值把相似声音归到注册库里，不是身份核验，绝不能当身份核验用。
- **标点和声纹各自加载一个模型。** 在 4 GB 板子上两个都开会压缩余量；设备输入项里可以分别关闭。
- **2026-09-06 的 RK3576 打包验证测的是 SenseVoice 识别与推理链路，不是 reSpeaker XVF3800 的采音通路。** 验证用的板子上没有接实体 XVF3800，5 条验收短句都是以文件方式喂入的（「POST /asr」 与 「/asr/stream」），没有经过真实麦克风。"PCM 音频到达语音服务"之后的部分已在真机确认；阵列自带的波束成形/回声消除和客户端的 ALSA 采集本次没有被实测覆盖。

### 设备本地转写

- **转写目录会无限增长。** 没有任何轮转机制。在部署跑上几个月之前，先定好保留期，用 cron 或运维流程执行。
- **是否保留音频是一个明确的选择。** 开着文件输出便于复核，同时也意味着设备上留着真实人员的录音。只要文字就把它关掉。
- **没有服务端的断档检测。** 盒子关了不会有人来提醒你。
- **「voice-client:c4-local」 镜像仍未发布。** RK3576 故障排查表里给出了一个真机确认可用的替代 tag（「sensecraft-voice-client:ovs-20260901b」），但它没有推送到任何 registry——新板子仍然需要自己构建，或拿到那个 tag 的拷贝。

### 服务端栈

- **容量按自己的试点定。** 先按 1–2 路并发作为工作假设，在自己的部署上实测之后再扩。
- **栈主机是 arm64。** 冻结镜像只有 arm64，随包的 ASR 镜像是 RK3576 NPU 构建。换主机类别需要你提供对应的 ASR 镜像。
- **说话人识别默认关闭。** 提供它的容器不启动，「speaker.identified」 恒为 false，按主体删除也没有声纹可级联。
- **令牌在 URL 里。** 浏览器 WebSocket 客户端不能设自定义头，所以 ASR 端点接受 「?token=」。出了可信局域网就要在它前面终结 TLS。
- **后台账号默认是 viewer。** 用 admin 凭据调改角色接口提权；在那之前用 admin API 令牌。
- **一套部署一套库。** 边缘采集端自带 MySQL 与 MinIO，因为冻结 compose 是一个整体；多个采集端指向同一套栈要改上报地址，这种布局请自行复测。
- **删除证明脚本不是跑在你的部署上的。** 它自己起 MySQL 与 MinIO 来证明删除路径——这既是它可复现的原因，也意味着它是关于代码的证据，不是关于你现场数据的证据。

## 许可说明

语音服务内含第三方模型——识别用 SenseVoice 和 Paraformer，标点用 CT-Transformer，声纹用 CAM++，端点检测用 Silero VAD。各自遵循其上游许可，商业使用需你与相应上游自行确认；本方案既不授予也不扩展任何相关权利。模型在首次启动时从部署时选定的镜像源下载。

服务端栈里的服务是 Seeed 自有的（「sensecraft-asr-service」、「sensecraft-voice-client」、「sensecraft-voice-service」、「sensecraft-voice-web」）。MySQL 与 MinIO 按各自许可从上游拉取——MySQL 是 GPLv2 加 FOSS 例外，MinIO 当前版本是 AGPLv3，把对象存储嵌进商业产品之前值得先读一遍。脱敏没有用第三方模型：姓名与地址词表用的是公有领域的《百家姓》与省级行政区名单。
