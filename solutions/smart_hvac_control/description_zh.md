## 这个方案能帮你做什么

办公楼、商场、工厂的中央空调通常按固定排程运行：不管楼层是满是空，设定值都一样。这个方案把暖通控制器和电能表汇入同一套点位模型，用建筑自己的历史数据训练 KNN 模型给出设定值建议，再写回控制器——但写入必须从现场读回、与下发值比对通过，才算生效。

系统默认处于"先观察"模式。在操作员显式开启控制之前不会写入任何点位；约束每次写入的安全限值在现场工程师批准之前一律标记为未批准。

## 你能得到什么

**暖通与能耗共用一套点位模型。** 暖通控制器可经 OPC UA、Modbus TCP/RTU 或 BACnet/IP 接入。电能表通过内置的 Eastron SDM630 模板接入（Modbus V2 寄存器映射，IEEE-754 float32 输入寄存器），覆盖三相电压电流、总有功功率（kW）、总功率因数、频率和进口有功电能（kWh）。该模板生成的是与人工填写完全相同的严格 CSV，因此内置模板和手写模板走同一个解析器、同样的 256 行上限。电表点位只读，计入 2,000 点的注册表总额，不占用 50 个可写点。

**用你自己的数据预测设定值。** 导入历史运行数据的 CSV 或 Excel 导出；KNN 模型学的是这栋楼，不是一条通用曲线。预测结果在被允许下发到控制器之前就可以查看。

**写入是核实过的，不是假定的。** 控制器返回 ACK 不等于现场真的动了。每次写入先冻结 last-known-good 的值、质量、时间戳和 BACnet 优先级，延迟后读回并按容差比对。读回值质量不为 good 时一律不算核实通过，无论数值是多少。

**五类触发条件下的回滚。** 读回不一致、数据源离线、预测被禁用、操作员中止、批次部分失败。BACnet 点位按原优先级发 Null 释放；Modbus 点位按施加顺序逆序恢复。补偿走与原写入相同的授权写入链路，因此无法绕过写使能开关和写策略。

**告警按成因归一，不按事件计数。** 五种告警类型——数据源离线、样本过期、写入失败、读回不一致、补偿失败——各自按成因标识，同一故障重复出现时复用已打开的告警，不会开出第二条。补偿失败是 critical，因为此时现场状态未知；其余四种是 warning，因为现场保持着原设定值。确认告警只记录操作员看到过，不清除成因；只有恢复事件能清除，且恢复事件带着它所清除的告警 id。

**有界的安全限值。** 设定值上下限、单位时间窗内的最大变化量、运行模式白名单。出厂默认值（18–30 °C、每 5 分钟 1 °C、off/fan/cool/heat/auto）被显式标记为未批准，在具名的现场工程师签字之前一直报告为 pending。

## 适用场景

| 场景 | 怎么用 |
|------|--------|
| 写字楼 | 用这栋楼自己的历史数据按区域预测设定值，先在观察模式下走完一个完整的人流周期，再选一个区域率先开启写入 |
| 商场 | 每层注册一块电表，让功率和电能与驱动它们的暖通点位并排显示，在信任任何一方之前先比对预测值与实际值 |
| 工厂车间 | 让预测与生产排班对齐，并把变化率限值收紧到一次换班无法把机组一步拉动 |
| 混合机组改造 | 把 OPC UA 冷机和 BACnet/IP 空调机组放进同一张点位表，两者共用一条控制链路和一份审计记录 |

## 实测边界

这不是一套安全认证的控制系统。它是带核实写入链路的监督式设定值推荐器；机组自身的联锁与安全控制仍然是最终裁决方，每次写入都限制在现场工程师批准的范围内。

以下数据来自开发硬件上的模拟器压测台，不是建筑现场数据。除非另有说明均为单次采样，全部未经独立复现。

| 指标 | 数值 | 条件 | 来源 |
|------|------|------|------|
| **节能率** | **未测** | — | 目前没有对照基线，没有天气与入住率归一化，也没有约定的统计周期。这里写任何百分比都是编的。在真实建筑上完成受控的前后对照研究之前不作任何声明 |
| 控制准入时延 | 最大 1.41 ms | n = 2 个周期，仅冒烟运行 | **冒烟实测。** 取自 `northbound-smoke` 压测台的 runtime 基线，上游 `f831bae`。两个样本说明不了带载系统的表现 |
| 预测周期时延 | 最大 46.27 ms | n = 4 个周期，仅冒烟运行 | **冒烟实测。** 同一份基线采集，同样的保留 |
| 采集吞吐 | 349.99 events/s（目标 350.0 的 99.99%），预测 0.939 cycle/s，进程组 RSS 峰值 217.3 MiB | 4 个协议源共 2,000 点，OPC UA/Modbus 5 s、BACnet 10 s，仅本机回环，**运行 180 s** | harvest-pi（Raspberry Pi 5，arm64），r14 `capacity-smoke`，上游 `b5fe4cc`。单次 180 s 运行——这不是稳定性结论 |
| 24 小时连续运行 | **结果待补** | 2,000 点，同样的采集周期 | harvest-pi 上的 24 小时 `release` soak 于 2026-09-05T05:01:19Z 启动、2026-09-06T05:01:19Z 结束，verdict 尚未取到；更长的 7 天与 30 天运行均未启动 |
| 电表精度与字节序 | **未在硬件上核实** | — | SDM630 寄存器地址依据厂商公开的 Modbus 协议文档，模板默认大端字节序与大端字序。在信任这些数值之前，必须有一个调试步骤用实际电表确认字节序 |
| 运行周期中的回滚与告警 | **未做端到端实测** | — | 回滚协调器与告警 envelope 各自有验收测试，但上游尚未把它们接进预测循环。开启写入之前请在自己的机组上验证 |

一个已知未决缺陷：预测循环是"跑完一个 cycle 再固定 sleep"，因此速率是 `1/(1.0 + t_cycle)`。2,000 点规模下 `t_cycle` 约 0.119 s，结构上限落在 0.894 cycle/s 附近，低于 soak 压测台强制的 0.90 门槛。第三轮每一次运行都复现，包括不注入任何故障的对照跑。要么改循环要么改门槛，目前两者都未改。

## 使用须知

**硬件**

| 项目 | 用途 | 必需 |
|---|---|---|
| reComputer R1100（或任意 x86-64 / arm64 Docker 主机） | 运行点位模型、预测、控制链路和控制台 | 是 |
| Eastron SDM630 电能表 | 提供功率与电能点位 | 走电表流程时需要 |
| USB 转 RS-485 适配器 | 仅当电表接在 RS-485 而非 Modbus TCP 上时 | 仅 Modbus RTU |
| 支持 OPC UA、Modbus 或 BACnet/IP 的暖通控制器 | 被读写的机组 | 做控制时需要；只做演练可用内置模拟器 |

**数据**

至少一周的历史运行数据（CSV 或 Excel），含时间、设定值、实测温度和用电量。导入需要几分钟。

**软件**

Docker Engine 20.10 及以上，约 1 GB 可用磁盘，主机 8280（控制台）和 4841（OPC UA 模拟器）端口未被占用。

## 注意事项

- **先观察再控制。** 至少让预测在不写入的状态下走完一个完整的人流周期。在把推荐值与机组实际行为比对过之前就开启写入，是监督层引发投诉的典型路径。
- **批准安全限值。** 出厂的 18–30 °C、每 5 分钟 1 °C 和五种模式白名单都是占位值。它们在具名工程师签字之前一直报告为未批准，应当替换为本机组实际调试出来的限值，而不是原样确认一遍。
- **确认电表字节序。** 厂商默认值并不通用。在相信缩放后的点位之前，先读一个物理量已知的寄存器核对。
- **Modbus RTU 需要串口设备部署配置。** 标准 Docker 配置不会挂载主机串口。在指定适配器与目标控制器通过真实硬件联调之前，生产写控制必须保持关闭。
- **仅限中央空调。** 本方案面向中央空调系统，不适用于分体式空调。
- **镜像 tag。** 已发布的镜像 `missionpack-knn:v1.6.5` 早于电表模板、回滚协调器和告警 envelope。承载这些能力的镜像尚未构建、尚未 push，不可变 tag 待定。按部署指南做调试步骤之前请先核对 tag。
