基于统一点位模型的暖通设定值优化：KNN 预测、Eastron SDM630 电能表接入、带读回核实的控制写入、回滚与告警。

## 套餐: 标准部署 {#default}

部署预测服务，注册电能表，并以"先观察"模式完成控制调试。在读回、回滚和告警都在自己的机组上实际走过一遍、且安全限值经具名工程师批准之前，写入保持关闭。

| 设备 | 用途 |
|------|------|
| reComputer R1100（或任意 Docker 主机） | 运行点位模型、预测、控制链路和 Web 控制台 |
| Eastron SDM630 电能表 | 经 Modbus TCP 或 RS-485 提供功率与电能点位 |
| 暖通控制器（OPC UA、Modbus 或 BACnet/IP） | 被读写的机组；只做演练时可用内置模拟器 |

**部署完成后你可以：**
- 得到从这栋楼自己的历史数据学出来的设定值推荐
- 在同一张表里看电表与暖通点位，SDM630 寄存器映射作为内置模板提供
- 让写入只有在现场读回值落入容差后才算生效
- 在五类触发条件下自动回滚，并得到按成因而非按事件标识的告警

**重要提示。** 这不是一套安全认证的控制系统，机组自身的联锁与安全控制仍是最终裁决方。每次写入都受限于出厂即为**占位值**的限值——18–30 °C、每 5 分钟 1 °C、off/fan/cool/heat/auto 模式白名单——在具名现场工程师签字之前，运行时一直报告该基线为未批准。**本方案包内不提供任何节能率数字**：目前没有对照基线、没有天气与入住率归一化、也没有约定的统计周期。

**前提条件：** Docker Engine 20.10 及以上 · 约 1 GB 可用磁盘 · 主机 8280 与 4841 端口空闲 · 至少一周的历史运行数据（CSV 或 Excel）

## 步骤 1: 部署暖通控制服务 {#hvac type=docker_deploy required=true config=devices/deploy.yaml}

部署预测与控制服务，并填写电表、控制模式、安全限值和告警参数。

### 前置条件

目标机上 Docker 正在运行，手边有电表的通讯方式与站号，以及暖通控制器的 OPC UA 地址——或保留默认地址以连接内置模拟器。

**控制模式**保持在 *observe*。在工程师真正批准限值之前，**安全基线批准人**留空——正是这个空值让基线持续报告为未批准。

### 部署目标 {#hvac_local type=local config=devices/deploy.yaml default=true}

部署到当前运行 SenseCraft Solution 的设备。适用于对着内置模拟器做演练，或本机就能访问机组网络的情况。

### 接线

`gallery/` 中已有运行界面的真实截图；现场接线照片暂缺，见 `gallery/ATTRIBUTION.md`。按以下方式接线：

1. 把本机接入与暖通控制器、电表（或其 Modbus TCP 网关）相同的网络。
2. 本目标不支持 Modbus RTU：标准 Docker 配置不会挂载主机串口。这里请用 Modbus TCP，或改用远程目标配合串口设备部署配置。
3. 保证 8280 与 4841 端口空闲，或在部署前释放它们。

### 故障排查

| 问题 | 解决方法 |
|------|----------|
| Docker 未运行 | 启动 Docker Desktop 或 Docker Engine 后重试 |
| 端口 8280 被占用 | 释放该端口，或在 compose 文件中修改主机端口映射 |
| 容器启动后退出 | 执行 `docker logs missionpack_knn`，最后几行是启动失败原因 |
| 网页打不开 | 等待 `/api/v1/health` 健康检查通过，启动预留 30 s |
| 电表点位能读但数值明显不对 | 这是字节序或字序不匹配，不是接线故障，见步骤 3 |

### 部署目标 {#hvac_remote type=remote config=devices/deploy.yaml}

通过 SSH 部署到机组网络中的 reComputer R1100 或其他 Linux 设备。电表接在 RS-485 上、或你的工作机访问不到控制器网络时用这个目标。

### 接线

设备实物与连接的真实截图暂缺，见 `gallery/ATTRIBUTION.md`。按以下方式接线：

1. 把设备网口接入控制器网络，并记录其 IP 地址。
2. 走 Modbus RTU 时接上 USB 转 RS-485 适配器，记下设备路径（通常是 `/dev/ttyUSB0`），并使用串口设备部署配置——标准配置不会把主机串口传入容器。
3. RS-485 的波特率、校验位和站号必须与电表上的配置一致；不一致时的表现是超时，而不是报错信息。

### 故障排查

| 问题 | 解决方法 |
|------|----------|
| SSH 连接失败 | 检查设备 IP、用户名、凭据，以及 sshd 是否在运行 |
| 远程设备无 Docker | 先在设备上安装 Docker Engine |
| 部署超时 | 检查设备能否访问镜像仓库 |
| 网页打不开 | 在设备防火墙上放行 8280 端口 |
| 容器内看不到 `/dev/ttyUSB0` | 标准配置不挂载串口设备，请改用串口设备部署配置重新部署 |

## 步骤 2: 打开控制面板 {#dashboard type=web_dashboard required=true config=devices/dashboard.yaml}

打开控制台，创建首个管理员账号，并确认步骤 1 配置的数据源处于在线状态。

### 前置条件

步骤 1 的容器必须处于健康状态。

### 故障排查

| 问题 | 解决方法 |
|------|----------|
| 页面无法加载 | 确认步骤 1 已完成且健康检查通过 |
| 主机/端口错误 | 远程部署时请用实际设备 IP 更新地址 |
| 某个数据源显示离线 | 检查可达性与站号；走 RS-485 时还要检查波特率和接线极性 |

## 步骤 3: 电表、控制链路与告警调试 {#commissioning type=manual required=true verify=true config=devices/commissioning.yaml}

注册电表、在观察模式下跑预测、有意走一遍失败路径，然后才开启写入。这一步决定这套部署能不能被信任，不要压缩流程。

### 前置条件

步骤 2 创建的管理员会话、能看到电表本机显示的现场条件，以及一位熟悉本机组的操作人员来判断推荐值是否合理。

**先看镜像 tag。** 执行 `docker inspect -f '{{.Config.Image}}' missionpack_knn`。已发布的 `missionpack-knn:v1.6.5` **不含** SDM630 模板、回滚协调器和告警 envelope。承载这些能力的镜像尚未构建、尚未 push，不可变 tag **待定**。运行在 v1.6.5 上时观察模式的子步骤仍然适用，电表、回滚和告警子步骤无法完成。

### 故障排查

| 问题 | 解决方法 |
|------|----------|
| 电表模板导入被拒绝 | 模板生成的严格 CSV 上限为 256 行；自定义模板超限时会被同一个解析器拒绝 |
| 电压和频率看着合理但数值不对 | 浮点字序问题。先在部署表单里切换字序重新读取，再考虑其他改动 |
| 进口电能出现倒退 | 仍是字序问题，或有两个数据源用不同站号在轮询同一台电表 |
| 写入有 ACK 但读回始终不通过 | 先看点位质量——读回质量不为 good 时一律不算通过，与数值无关 |
| 回滚本身失败 | 这会触发 critical 级的 compensation-failed 告警。此时现场状态未知，请人工恢复，在查清原因前不要重新开启写入 |
| 同一故障每次都开出新告警 | 告警按成因归一；出现重复说明成因字段不同，对比数据源与点位 id |

### 部署完成

**再次提醒。** 这不是安全认证的控制系统。已知弱点：上游尚未把回滚协调器和告警 envelope 接进预测循环，两者都需要在自己的机组上验证；电表的字节序与字序是厂商默认值而非实测事实；节能率没有任何实测数据。

#### 快速验证

1. `docker inspect -f '{{.Config.Image}}' missionpack_knn` 返回的是你打算运行的 tag。
2. SDM630 的十个点位全部可读，电压、频率和进口电能与电表本机显示一致。
3. 进口有功电能只增不减，且在数据源重启后保持累计值。
4. 已在观察模式下跑完一个完整人流周期的预测，推荐值经机组操作人员审阅。
5. 安全限值已填入批准人姓名，基线不再报告为未批准。
6. 一次在限值范围内的写入产生了命令回执、容差内的延迟读回，且点位质量为 good。
7. 数据源离线、读回不一致、样本过期三类故障各自产生了预期的告警，前两类各触发一次回滚：BACnet 按原优先级发 Null 释放，Modbus 逆序恢复。
8. 若启用了北向上云，`GET /system/runtime-metrics` 中的 `northbound.spool.queued` 为 0 且 `dropped` 未增加。

#### 需要导出的证据

交接记录需要：镜像 tag；电表模板 id 与确认后的字序；批准的安全限值与批准人姓名；已核实写入的命令审计记录；故障注入产生的回滚日志条目；带确认状态的告警历史。容器日志按 10 MB 轮转、保留 4 份（`docker logs missionpack_knn`），需要的内容请在被覆盖前拷出来。

#### 下一步

1. 先只在一个区域开启写入，观察满一个周期再扩大范围。
2. 对 critical 级的 compensation-failed 告警设告警通知；它是唯一意味着现场状态未知的一类。
3. 机组每次再平衡后重新批准安全限值——一条与机组不再匹配的已调试限值比占位值更糟，因为它看上去是批准过的。
