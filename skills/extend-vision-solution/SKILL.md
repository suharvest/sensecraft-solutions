# Extend Vision Solution

把一个已在某台设备上跑通的 AI 视觉方案，扩展到其他边缘平台，并给出**能横着比**的数据。

本 skill 只讲扩展与实测。方案契约（device YAML 字段、guide.md 语法、preset 规则）以
`spec/CONTRACT.md` 为准，创作流程见 `/author-solution`。

---

## 为什么需要它

跨设备扩展最容易产出的不是"多支持了几个平台"，而是**一张看起来能比、实际不能比的表**。
本 skill 的核心是测量纪律：先把口径钉死，再谈数字。

第二个高频问题是**厂商运行时**——每个 NPU 平台都有一套与内核耦合的用户态库，镜像里baked
一份就会和板子上的驱动对不上。第三个是**没有实机验证就声明支持**。

---

## Phase 0：先判断值不值得扩

回答三个问题再动手：

1. **模型能过去吗？** 目标平台需要什么格式（`.rknn` / `.hef` / TensorRT engine / `.cvimodel`），
   转换工具链在哪、要不要标定集、是否需要 x86 授权 SDK。
2. **后处理能过去吗？** raw-head 解码、NMS、跟踪、时序模型这些是不是纯 CPU/numpy 的？
   如果绑死在某个平台的算子上，扩展成本会翻倍。
3. **时序/状态类模型要不要重训？** 如果方案含时序判定（跌倒、行为识别），**每个平台必须用
   自己的姿态输出重新抽取轨迹并重新冻结权重**，不能跨平台借用——不同前端的关键点分布不同。

任何一项答不上来，先做可行性验证，不要先写 preset。

## Phase 1：钉死测量口径（最重要）

**这一步没做好，后面所有数字都是废的。**

### 1.1 固定模型

同一张表里的所有行**必须是同一个模型、同一个输入尺寸、同一种量化**。

- ❌ Jetson 跑 YOLO11s、RK 跑 YOLO11n，然后放同一张表比 ms
- ✅ 全部固定 YOLO11n 640²，精度不同的**拆成两张表**（FP16 一张、INT8 一张）

表头必须注明**模型名 + 尺寸 + 量化**。某个平台确实拿不到同尺寸模型时，在该行加脚注说明，
并明确它跑的是更大/更小的模型——不要让读者误以为在比硬件。

### 1.2 分清三种口径，永远不要混

| 口径 | 含义 | 典型来源 |
|---|---|---|
| **加速器推理** | 只有 NPU/GPU 的那一次调用 | `trtexec`、`rknnlite.inference()`、`hailortcli benchmark` |
| **pipeline** | 预处理 + 推理 + 解码/NMS | 应用自己的计时字段 |
| **端到端** | 再加解码、跟踪、时序、消息发布 | MQTT 消息间隔 |

**每个平台的计时字段范围都不一样，必须查源码确认，不能看字段名猜。** 本项目实测：

- Jetson 的 `inference_time_ms` 其实是 pipeline 范围（含预处理与 NMS）
- reCamera Pro 的 `inference_time_ms` 是纯 NPU（letterbox 在计时外）
- reCamera 2002 只有一个 detectAll 范围的计时器，**分不出加速器**，且是整数毫秒
- Hailo 上报的 `pipeline_ms` 是一个探针区间，不含解码与跟踪

确认方法：`grep` 计时变量的赋值位置，看 `t0`/`t1` 卡在哪两行之间。

### 1.3 测量条件必须写进文档

这些条件不写明，数字就不可复现：

- **是否锁频。** 实测 reCamera Pro 的 NPU 在 `rknpu_ondemand` 下停在 800 MHz（上限 950），
  同一块板仅频率档位就差 **23%**。RK3576/3588 实测常驻顶档，Jetson 记 `nvpmodel` 模式。
- **共存负载是否停掉。** 只有当共存业务**占用同一个加速器**时才会影响——曾出现 Orin NX 因自身
  GPU 业务测出 264.9 FPS、低于 Orin Nano，停掉后 306.2 FPS，排名直接反转。
- **输入是什么。** 合成空白帧 vs 真实画面差别很大：有目标才会触发解码/NMS。

### 1.4 准确率：给方法和一个数，不要做排名表

小测试集上的准确率**没有区分平台的分辨率**。本项目 27 段片段 = 3.7 个百分点/段，多个平台会
落在同一个数值上。

正确做法：写清**测试协议**（数据集、按人划分、哪些用于训练/选阈值/只读一次、重采样帧率、
提前报警如何计），然后给**平均值和区间**。不要做成平台对比表——那会让读者以为分辨得出差异。

### 1.5 并发：区分"推理上限"和"建议路数"

- **推理上限路数** = 聚合吞吐 ÷ 目标帧率，只算加速器，是理论天花板
- **建议路数** 要打折——实测端到端吞吐通常只有推理上限的 28%–44%，因为解码、跟踪、状态机、
  消息发布都要占 CPU 和内存带宽

两个都给，并说明建议路数的依据。

详细协议见 `references/measurement-protocol.md`。

## Phase 2：移植运行时

### 2.1 厂商库从宿主挂载，不要 baked 进镜像

NPU 用户态库必须和板子上的内核驱动版本匹配。镜像里固定一份，换块板子就崩。

```yaml
volumes:
  - /usr/lib/librknnrt.so:/usr/lib/librknnrt.so:ro     # RK
  - /usr/lib/libhailort.so.4.21.0:/usr/lib/...:ro      # Hailo，ABI 锁版本
```

**Python 包不要直接挂载到镜像的 site-packages。** 厂商包常以 wheel 形式装在 venv 或
`~/.local`，源路径不存在时 **Docker 会创建一个空目录**并覆盖掉镜像自带的包，容器崩溃循环。
正确做法：部署时把需要的包**拷贝**到一个暂存目录再挂载。

### 2.2 PYTHONPATH 要追加，不要覆盖

镜像若把 apt 装的模块靠 `PYTHONPATH` 串起来，你覆盖它就切断了所有 apt 模块：

```yaml
PYTHONPATH: /host-pysite:/usr/lib/python3/dist-packages   # 追加
```

### 2.3 GStreamer 硬件解码的三个坑

1. **`h264parse` 在 `gstreamer1.0-plugins-bad` 里**，基础镜像通常没有。装整个包会拉 ~300 个
   依赖（+500 MB），用 builder stage 只拷 `libgstvideoparsersbad.so` + `libgstcodecparsers`。
2. **厂商插件（如 `mppvideodec`）要连同它链接的 soname 一起拷**，`find | head -1` 可能抓到
   `.so.0` 而插件要的是 `.so.1`——拷全部版本。
3. **GStreamer 会缓存插件扫描结果**（`/root/.cache`），新暂存的插件不会被重新发现。
   给该目录挂 tmpfs。

### 2.4 镜像瘦身：先看依赖链再删

用 `docker history` 找大层，用 `apt-cache rdepends --installed` 追依赖链。本项目实测：
`gir1.2-gst-plugins-base-1.0` 经 `libgstreamer-gl1.0-0 → libgl1 → mesa → libllvm15` 拖进
**150 MB OpenGL 栈**，而应用只把视频解成 RGB 数组，从不碰 OpenGL。

另一个常见浪费：`COPY /wheels` 后 `RUN pip install && rm -rf /wheels`——**删除只是新层标记
不可见，wheel 仍在镜像里**。改用 BuildKit 的 `RUN --mount=type=bind,from=builder`。

## Phase 3：实机验证（不做完不许声明支持）

### 必须实机跑的

- 部署走**引擎的正式路径**，不是手工敲命令或直接调 deployer
- 确认**功能真的在跑**：容器 healthy 不等于在工作，要看有没有输出消息、检出结果是否合理
- 确认**走的是预期路径**：日志里那行 `video=` / `backend=` 要看，静默降级很常见

### 声明 `verified: hardware` 的门槛

其他 preset 标这个的依据是**观测到实际业务输出**（如 MQTT 里有人被跟踪、状态跃迁）。
只做到"部署成功、容器起来了"不够格。够不着就别标——空着比虚标好。

### 验证脚本的纪律

- **改了被测对象的配置必须还原。** 曾因 A/B 脚本把 backend 留在 `opencv_ffmpeg`，导致下一轮
  "验证通过"其实测的是另一条路径
- **依赖服务要一起起。** 只起应用不起 broker，会得到一堆连接拒绝和空的采集文件
- **不要用 `docker compose restart` 应用新配置**——它不重读 compose，换 image tag 或改环境
  变量必须 `up -d <service>`

## Phase 4：文档呈现

### 表格规则

- **行序按产品线**，不按性能高低排（本项目：reCamera 2002 → Pro → RK3576 → RK3588 →
  reComputer R → reComputer J）
- 精度不同**拆表**，不要在一张表里混 FP16 和 INT8
- 每张表**注明输入是什么**（合成空白帧 / 真实画面）和**口径是哪一层**
- 某平台某列填不了就**留空并加脚注说明为什么**，不要用近似值凑满

### 文案纪律

- 只写可验证的事实和数字，判断留给读者
- 推断必须标注为推断，不要和实测混排
- 绝对表述（"所有平台都…"）写之前先数一遍

## 最后：本项目实际犯过的错

这些不是假想，是这轮扩展里真实发生并被纠正的：

| 错误 | 后果 | 教训 |
|---|---|---|
| 拿**不等吞吐**下的 CPU 绝对值比较 | 关于硬件解码收益连续下了 4 个错误结论 | 比 CPU 必须先对齐吞吐 |
| 隔离测量脱离真实负载 | 收益高估一倍（21.9 vs 10.1 ms） | 以生产条件下的对照为准 |
| 单次采样当结论 | 把噪声（62 vs 58 ms）当成真实差异并据此提出假设 | 交叉重复测量再下结论 |
| 用 `docker stats` 采样测突发负载 | 样本 60%–352%，均值不可信 | 用 cgroup 累计计时 |
| 没锁频 | 同板 23% 差异被当成性能退化 | 记录并锁定频率 |
| 把 load average 当争用证据 | 误判方向，白查一轮 | D 态线程也计入 load，看实际 CPU |
| `num-buffers=N` 造成的丢帧假象 | 误判解码器在丢帧 | 测吞吐不要限制消费端 |
| 写代码前不读契约 | 返回类型和回调签名全错，真机跑挂 | 先看基类和同类实现 |
| 假设模板会递归展开 | 占位符原样写进设备，应用崩溃 | 嵌套结构自己验证 |
| 不看 `git log` 就解释现象 | 关于同一个问题连续给了 2 个错误原因 | 先查仓库状态再推理 |

**共同点：大多数错误不是不会做，而是没验证就下结论。** 每次给出结论前，问一句"这个数字是我
测的还是我推的"。
